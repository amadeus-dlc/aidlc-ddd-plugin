## 比較範囲を限定して検証した

[試作](../../experiments/rust-syn/)はsyn 3.0.5をCargo.tomlで固定し、Cargo.lockも管理する。現行実装はBun／TypeScriptとtree-sitter-rustのWASMを使う。両方に同じソースを渡し、[検証スクリプト](../../scripts/verify-rust-syn.ts)で31ケースを検査した。このうち実際のドメインセンサーとの比較は5ケースで行い、別途6種類の不正なプロトコル入力を拒否することも確認した。31ケースの検証成功は、31本のRustコードが正しいという意味ではない。意図的なコンパイルエラーや検査不能ケースを含む。

試作で実装した範囲:

- 公開フィールドのルール`a`について、名前付き・タプル構造体の候補を抽出する。制限付き公開、raw識別子、Unicode、行番号を扱う。
- impl・trait・自由関数のシグネチャ、レシーバー形式、戻り値の型表記、enumのバリアント、型別名、import、モジュール、メソッド呼び出しを抽出する。
- `return self.amount;`を含め、フィールドを返すメソッドの構文形状を識別する。getter呼び出しのルール`d`全体や、副作用の有無は検証しない。
- テストしたマクロ、属性・derive、条件付きコンパイル、外部モジュール、不正構文、union、未対応修飾子を検査不能として報告する。

実センサーとの比較対象は`a`と`d`である。通常の名前付きフィールドと末尾式getterの合否は、従来の挙動と一致した。センサー全体の同等性、正規成果物のスキーマ、コマンド・生成時エラーの集合、所有に伴う効果、業務不変条件は、この試作の対象外である。

## 2つの抽出器とゲートの判定は別の問いに答える

規則`a`と`d`はネイティブ抽出器の事実で判定する（T-10-02）。したがって下表のtree-sitter列はその抽出器自身の出力であり、ゲートの判定ではない。判定列は、現在`ddd-rust-domain`がその入力に対して報告する内容である。

| 入力 | tree-sitter抽出器 | ネイティブ抽出器 | `ddd-rust-domain`の判定 |
|---|---|---|---|
| 非公開の名前付きフィールド | `a`のフィールドなし | `a`のメンバーなし | `a`の指摘なし |
| `pub amount: u64` | `a`のフィールドを抽出 | `a`のメンバーを抽出 | `a`を指摘 |
| `pub struct Invoice(pub u64);` | `a`のフィールドなし | `a`のメンバーを抽出 | `a`を指摘 |
| `pub struct Invoice(pub(crate) u64, u64);` | `a`のフィールドなし | `a`のメンバーを抽出 | `a`を指摘 |
| 末尾式`self.amount`のgetter | getterの構文を認識 | getterの構文を認識 | 呼出行で`d`を指摘 |
| `return self.amount;`のgetter | getterの構文を見落とす | getterの構文を認識 | 呼出行で`d`を指摘 |

判定が変わったのは、公開タプルメンバー2件と明示的`return`のgetter 1件の計3行である。検証スクリプトはこの3件と、判定が変わらない対照2件を実センサーへ通し、ケースごとの両方の件数を[実行記録](evidence/rust-syn-spike.json)の`actual_sensor_comparisons`に残す。[cases.json](../../experiments/rust-syn/cases.json)の`treeSitterFields`と`treeSitterGetters`は意図的に空のままである。tree-sitter抽出器はこれらの形式を今も見落としており、その修正はT-10-02の対象外だからである。処理速度の優劣は比較していない。

## 規則`a`・`d`がtree-sitterから読み続ける範囲

ネイティブの事実が決めるのは、メンバーが公開かどうかと、メソッド本体が`self`のメンバーを返すだけかどうかである。その事実を所見に変える処理は、引き続きtree-sitter抽出器が担う。残る境界は次のとおり。

- 対象ファイルの集合。Cargoワークスペースの走査、層の割当、[`rust-modules.ts`](../../tools/ddd/lib/packaging/rust-modules.ts)の`mod`探索が、ネイティブ抽出器へ渡すバッチを決める。
- 型の解決。`impl`ブロックと宣言の対応付け、呼び出しの受信型の解決は[`program.ts`](../../tools/ddd/lib/rules/rust/program.ts)が行う。ネイティブの応答は、照合キーとしての自己型のテキストしか持たない。
- 呼び出し箇所。規則`d`の呼び出し、受信側の表記、リポジトリ引数の例外判定は、tree-sitterの呼び出し情報から得る。
- 申告ファイルのマクロ由来の未解析領域と構文エラーは、引き続きtree-sitterの解析結果から報告する。

ネイティブ応答の限界のうち2点は、記録するだけで判定には使わない。属性マクロ・deriveマクロは解析器が見ない項目を追加しうるが、注釈した宣言自身のメンバーは変えられないため、出現ごとの記録は行わない。項目マクロと`cfg`／`cfg_attr`は`domain-facts.unresolved`のnoteとして判定に添える。規則`a`・`d`が判定する申告ファイルを持つ実行では、解析器が受理できなかったファイルをnoteで済ませるのは、これらの規則の判定元となるファイル（ゲートが検査する申告ファイルと、domain層クレートの全ソース）に含まれない場合に限り、含まれる場合はnoteでは済ませず、ゲートを検査不能として停止し、抽出器が返した理由を報告する。「このファイルは公開メンバーを宣言していない」は、読めなかったファイルについて出してはならない唯一の答えだからである。

## 構文解析だけでは名前や型を解決できない

synの公式資料は、Rustのトークンを構文木へ変換する役割を説明している。`parse_file`はソース文字列を受け取り、editionを指定する引数は持たない。利用側では、修飾子や非網羅的な列挙型、Verbatimノードなどの未対応構文も扱う必要がある。[syn API](https://docs.rs/syn/3.0.5/syn/)、[parse_file](https://docs.rs/syn/3.0.5/syn/fn.parse_file.html)、[ソース位置の取得](https://docs.rs/proc-macro2/latest/proc_macro2/struct.Span.html)を参照。

検証スクリプトはrustcと比較し、次の限界を実測した。

- 存在しない`MissingType`や、戻り値`u64`に文字列を返す関数も構文解析には成功する。rustcは拒否するため、構文解析の成功だけでは型に依存するDDD規則を判定できない。
- 型別名`Outcome<T>`、再公開されたエラー、`Self::Error`の表記は取得できるが、参照先の型は未解決のままである。アプリ独自の`Result<T, E>`も解析できるため、`Result`という名前だけでは標準の結果・エラー契約と判断できない。
- 型推論を要するレシーバーの呼び出しも解析できるが、その型の解決には対応していない。
- 同じ`async fn`のソースは両試行で解析できるが、rustcはedition 2015で拒否し、2018で受理する。対照用の単純な構造体は2015/2018/2021/2024でコンパイルできた。edition境界を調べた結果であり、全editionへの対応保証ではない。
- マクロが生成するフィールドは、展開前の構文には現れない。一方、偽になる`cfg`配下のフィールドは構文上は存在する。試作は両方を検査不能とし、候補を残しても違反確定には使わない。
- `mod line;`を持つ`invoice.rs`と`invoice/mod.rs`は、どちらも外部モジュールの読込が必要と報告する。子ファイルの探索や、プロジェクトのモジュール配置設定の検査は行わない。

Cargoのワークスペース・ターゲット・featureの把握、ファイルやクレートをまたぐimport・型別名、型引数の置換、traitの解決、マクロ展開、有効な`cfg`の選択は、別途設計する必要がある。`cargo check`の成功はコンパイラが受理した証拠になるが、独自DDD検査が必要とする解決済みシンボルを、それだけで取得できるわけではない。

## 検証した環境ではネイティブ実行ファイルを単独で動かせた

releaseバイナリを新しい一時ディレクトリへコピーし、PATHを空のディレクトリに向け、親の環境変数を引き継がずに実行した。実行時にCargo・rustc・Bun・tree-sitterは不要だった。検証したApple Silicon Macでは、シンボル除去後の実行ファイルは約1.86 MBで、動的リンク先はシステムの`libSystem.B.dylib`だけだった。入力のハッシュ、厳密なバージョン、容量・依存先、所要時間、各ケースの結果は[実行記録](evidence/rust-syn-spike.json)に残した。

試作のビルドにはRustツールチェーンと、初回はcrates.ioへのアクセスが必要になる。検証スクリプトにはBunと既存のWASM資産も必要である。現在のプラグイン利用者にRustの導入を要求する変更ではない。

本番配布では、対応するOS・アーキテクチャを決め、各環境向けのバイナリをビルドして公開する必要がある。チェックサムと実行権限、新規導入・更新、バイナリ欠落時の扱いも検証する。センサー実行時のソースビルドは避ける。WASM化も配布方法の候補だが、今回は試していない。Linux、Windows、x86_64、最低OS・Rustバージョン、プラグインの導入・承認処理との接続は未検証である。

## 再実行して結果を確認する

リポジトリのルートから実行する。

```sh
cd ddd
bun run experiment:rust-syn
# 管理対象の実行記録を明示的に更新する場合:
bun run experiment:rust-syn --write
cargo fmt --manifest-path experiments/rust-syn/Cargo.toml --check
cargo clippy --locked --manifest-path experiments/rust-syn/Cargo.toml --all-targets -- -D warnings
```

このコマンドは`--locked`でビルドし、テスト入力と実センサーを比較する。コンパイラを対照にするケースではrustcを実行し、バイナリ移動後の動作と出力の再現性も確認してJSONを出力する。検証に失敗すると終了コードは非ゼロになる。`treeSitterFields`／`treeSitterGetters`はtree-sitter抽出器が今も見落とす内容を記録し、検証スクリプトの`SENSOR_EXPECTATIONS`はゲートの判定を記録する。本番修正が実際に動かした側の期待値と本書を、同じ変更で更新する。

試作実行ファイルは標準入力から1件のJSONリクエストを受け取る。以下のプロトコル1は試作専用である。センサーが読むのは[ネイティブ抽出器の配布](native-extractor-distribution.ja.md)に記載した`domain-facts`プロトコルであり、この形式ではない。

```json
{"protocol_version":1,"files":[{"path":"invoice.rs","source":"pub struct Invoice(pub u64);"}]}
```

出力には`field_inspection.state`（`pass`・`violation`・`unresolved`）、フィールド候補、構文情報、`semantic_analysis: "unsupported"`を含む。`pass`は限定されたフィールド検査だけの判定である。終了コード0は検査不能を含む報告の出力成功を意味する。不正なリクエストは終了コード2となり、標準エラーに理由を出し、標準出力は空にする。この形式は試作用で、現行センサーの判定契約や今後の共通スキーマとは異なる。synのノードをプロセス外へ渡さず、プロジェクト全体の合格判定も出さない。

## 共通設計へ反映する項目

[言語共通の契約](language-independent-design.ja.md)を設計の基準とする。T-09では[検査設計](inspection-contract-design.ja.md)に沿って、ルールごとに必要な情報、解決・完全性の状態、共通の判定処理と言語固有解析の境界を実装する。T-10-02では、公開タプルフィールドの2ケースと明示的なreturnを持つgetterを規則`a`・`d`で解消し、両モジュール配置で確認した。残るRust規則の移行、モジュール配置検査、tree-sitter資産の削除は未着手である。必須情報を解決できない場合は承認を止め、TypeScript Compiler API側も同等の業務シナリオで同じ契約を検証する。
