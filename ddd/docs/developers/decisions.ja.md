## 2026-09-13: 言語共通の契約とリリース順序

状態: 設計は合意済み、実装は未完了。[共通設計](language-independent-design.ja.md)に仕様を集約し、Rustの現状と目標を比較する。

RustとTypeScriptを同じドメイン規約・検査契約に照らして改善する。実行ホストとレイヤー別パッケージを分け、型だけの参照も含めて公開境界と依存方向を強制する。集約の実行モデル、永続化、コード表現、モジュール配置は独立した選択とする。生成時を含む業務エラーをメソッド固有の閉じた型にし、必須の検査が不能なら承認を止める。両言語で状態隠蔽、不変性、可変参照の分離を守る。

TypeScriptはclass方式か構造体＋コンパニオン方式をプロジェクトごとに選ぶ。後者はクロージャ内の状態と非公開のunique symbolブランドを使い、classは#プライベートフィールドを使う。Domain PrimitiveとValue Objectにも適用する。Resultは言語拡張用のinfrastructureに置き、neverthrow・Effect・fp-tsとの個別統合は今回の対象外とする。初回のTypeScript統合対象は、サーバー側のNode.js runtimeで動くESMのNext.jsアプリとする。

最初に共通の比較シナリオを定義し、小さなTypeScript実装で共通部分を検証する。最初のリリースには共通契約、Rustの改善、既存Rust成果物の明示的な移行を含める。TypeScriptの全面対応は次のリリースで行う。共通の変更ごとに仕様・ナレッジ・ステージ・センサー・振る舞いテストを揃える。

TypeScriptの解析はCompiler APIを使い、型に依存する検査はProgram・TypeCheckerの情報を根拠にする。依存は言語固有の実装内に置き、RustとTypeScriptから同じ共通検査契約へ情報を渡す。T-09の検証実装から採用してT-11へ引き継ぎ、APIバージョンの互換性も検証する。

## 2026-09-13: 共通検査契約のもとでRust＋synを採用する

状態: [構文解析の試作](rust-syn-spike.ja.md)後に採用方針を承認。本番への置き換えは未完了。Rustの構文解析にRust＋syn、TypeScriptにはCompiler APIを使う。言語固有の走査・解決を各実装に閉じ、DDDの判定の意味は共通規則が所有する。TypeScript内のRust固有の解析処理を減らし、ドメイン方針を統一する。

synはコンパイラの型推論、trait解決、マクロ展開を提供しない。[検査設計](inspection-contract-design.ja.md)ではCargoの条件と明示的な参照解決を組み合わせ、完全性を記録し、必須情報が未解決なら承認を止める。不在の証明と根拠不足、解決したシンボルの識別とアクセス許可を分ける。業務IDは正規モデルが所有し続ける。

tree-sitterを維持して現行の抽出処理を修正する案も成立した。実測したタプル・getterの見落としは実装の欠落であり、パーサー自体の限界ではない。採用する方向はRustによるネイティブ解析とし、全規則の互換性と環境ごとの配布を今後検証する。小規模な試作だけでコンパイラ内部の意味解析基盤を選定したり、リリース可能と判断したりしない。

## 2026-09-25: tree-sitter 資産は比較用に残さず撤去する

状態: 適用中。T-10-05 の時点で、出荷されるすべての Rust センサーが報告するすべての規則はネイティブ抽出器で判定しており、tree-sitter に残っていたのは2つの答えだけだった。申告ファイルを読めたかどうかと、そのマクロ由来の未解析領域の位置である。この2点のために約1MBのパーサーと文法を維持する案は採らない。前者は通常のファイル読み取りであり、後者は再実装せずに落とす。ネイティブ側は、モジュール宣言を隠しうる項目マクロと `cfg`／`cfg_attr` を既に拒否し、それ以外の位置では既に note を添えているため、手放すのは式の位置に書かれたマクロと組込みでない属性マクロの報告だけである。既存の拒否は後者を扱わない。属性マクロは適用先の項目を置き換えられるため、それが隠すものは未解決のまま残る。その扱いはその後 [#80](https://github.com/amadeus-dlc/aidlc-ddd-plugin/issues/80) で決まり、次の決定に記録した。代替の note を新設することは規則の新設にあたり、本変更の要求ではない。

代償は、tree-sitter の答えをこのリポジトリから比較対象として得られなくなることである。先行タスクが「置き換えた列挙がここで何を報告していたかは確定できない」と記録した箇所は、保留ではなく、ここでは恒久的に未確定になる。この点は親課題向けに[完了タスク](completion-tasks.ja.md)へ記録する。代替案として、出荷コードが読まない比較用の文法だけを残す案も検討したが採らない。製品が使わない資産は最新の状態に保たれず、古くなった比較対象は問いとは別の問いに答えるためである。

## 2026-09-26: 組込みでない属性は属性マクロの可能性があるものとして扱い、同じ項目の derive が使う補助属性のうち許可リストに載せたものだけを除く

状態: 適用中（[#80](https://github.com/amadeus-dlc/aidlc-ddd-plugin/issues/80)）。属性マクロは注釈した項目を置換するため、規則 `a` が報告する公開メンバーや、規則 `d` が報告する getter を追加しうる。そのため規則 `a` は、そうした項目を所見なしで合格させえた。derive マクロは注釈した項目を変えられないが、構文だけでは、その補助属性と同名の属性マクロを区別できない。そこでネイティブ抽出器は `protocol_version` 7 のもとで、組込みでもなく、同じ項目の derive の補助属性として許可リストに載ったものでもない属性をすべて、理由 `attribute-macro` の `unresolved` として記録する。`ddd-rust-domain` と `ddd-rust-use-case` は、規則 `a`・`d` の判定元となるファイルにその記録があれば、検査不能として停止する（終了コード 127、verdict なし）。それ以外のファイルとゲートでは note にとどめる。組込み属性の一覧、許可リスト（`Serialize`・`Deserialize` の `serde` と、`Default` の `default`）、ゲートの動作は[属性マクロの扱い](rust-syn-spike.ja.md#属性マクロの扱い)に記載する。

2つの代替案は採らない。許可リストを規則層に置く案は、何を記録するかの判断を、項目を見ている抽出器から切り離す。さらに、補助属性がどの項目に付いているかを伝える protocol の項目が別に必要になる。許可リストの補助属性をファイル全体で許可する案は、serde の derive を持たない項目の `#[serde(...)]` まで通してしまう。そこはまさに属性マクロでありうる位置である。`cfg` の評価は #80 の対象外であるため、`cfg_attr` が適用する中身は読まない。パスで修飾された属性は常に記録する。再公開された組込み属性と見分けるには名前解決が必要だからである。

## 整合性と回復の方針

失敗時の保証は、ドメイン操作、単一集約保存、結果不明、複数集約の途中失敗ごとに定める。複数集約のフローでは途中コミットが残り得るため、再試行・補償・中間状態を設計する。

冪等性には要求の識別と再送条件に合う保持期間が必要になる。初回の状態変更成功と、新規イベント0件の重複成功を区別する。戻り値の具体型はT-03で決定する。

サーガの実装方式、保存基盤、配送の順序保証は個別の要件と条件で選ぶ。根拠と条件は設計3文書に記載する。

## T-01の成果物接続

標準の成果物名に従い、正規YAMLをMarkdownへ包んで配布する。ユースケース・層構造は既存レビュー成果物の必須セクションとし、Unit種別を拡張しない。通常承認の接続を検証したが、標準の単独完了は成果物なしでも完了するため別課題として残す。理由と検証範囲は[成果物契約](../users/artifact-contract.ja.md)に記載した。

## T-02のRust判定

ドメイン層の型名全体を集約扱いせず、正規モデルのroot_elementと明示的なRust型を結び付ける。呼出し先はモジュール・use・単純な型別名・明示された引数やフィールドから照合し、型推論とtraitの実装選択は行わない。曖昧な箇所は注記する。

集約写像のreplay_methodsへメソッドとイベントIDを記録する。保存方式・配置・所属集約・イベント引数型が一致する場合だけ規則bの例外とする。既存モデルのスキーマは変更せず、メソッド本体の意味的な正しさはレビュー・テストに残す。[判定契約](../users/rust-sensor-contract.ja.md)を参照。
