## The comparison is deliberately bounded

The [experiment](../../experiments/rust-syn/) uses syn 3.0.5, pinned in Cargo.toml, with a committed Cargo.lock. At the time of this comparison the production implementation used Bun/TypeScript and tree-sitter-rust WASM, and both implementations received the same source text; since T-10-06 the production implementation is this extractor, so the comparison is a historical measurement rather than a current one. The [verifier](../../scripts/verify-rust-syn.ts) checks 31 source cases, runs 5 cases through the real domain sensor, and rejects 6 malformed protocol inputs. Thirty-one successful experiment assertions are not thirty-one valid Rust programs: some inputs intentionally fail compilation or require unresolved inspection.

Implemented in the experiment:

- Rule `a` candidates for non-private named and tuple struct fields, including restricted visibility, raw identifiers, Unicode, and line locations.
- Syntax facts for impl/trait/free-function signatures, receiver forms, textual return types, enum variants, aliases, imports, modules, and method calls.
- A field-return shape recognizer, including explicit `return self.amount;`. It is not a complete implementation of getter-call rule `d` or a proof about effects.
- Explicit unresolved results for tested macros, attributes/derives, conditional compilation, external modules, malformed syntax, unions, and unsupported modifiers.

The actual sensor comparison covers `a` and `d`. Its normal named-field and tail-expression getter cases agree with the earlier behavior. Whole-sensor equivalence, the canonical artifact schema, command/factory error membership, ownership effects, and business invariants are outside this prototype.

## The two extractors and the gate verdict answer different questions

Every rule `ddd-rust-domain` reports decides on the native extractor's facts (T-10-02 for `a` and `d`, T-10-03 for the rest), so the tree-sitter column below is that extractor's own output and was never the gate's answer after T-10-02. T-10-06 removed that extractor, so the column is the 2026-09-13 measurement of an implementation this repository no longer contains; it cannot be regenerated here. The verdict column is what `ddd-rust-domain` reports for the input today.

| Input | tree-sitter extractor | native extractor | `ddd-rust-domain` verdict |
|---|---|---|---|
| Private named field | No `a` field | No `a` member | No `a` finding |
| `pub amount: u64` | `a` field | `a` member | `a` finding |
| `pub struct Invoice(pub u64);` | No `a` field | `a` member | `a` finding |
| `pub struct Invoice(pub(crate) u64, u64);` | No `a` field | `a` member | `a` finding |
| Getter with tail expression `self.amount` | Getter syntax recognized | Getter syntax recognized | `d` finding at the call |
| Getter with `return self.amount;` | Getter syntax missed | Getter syntax recognized | `d` finding at the call |

The three rows whose verdict moved — the two public tuple members and the explicit-`return` getter — are the cases this migration changed. The verifier runs each of them plus the two unchanged controls through the real sensor and records both counts per case in the [execution evidence](evidence/rust-syn-spike.json) under `actual_sensor_comparisons`. Which experiment cases it also runs through the sensor is read from `SENSOR_EXPECTATIONS` in the verifier; the empty `treeSitterFields` and `treeSitterGetters` baselines that used to select them were removed with the extractor that filled them, along with the `tree_sitter_fields` and `getter_comparison` columns of each recorded case. The experiment makes no comparative speed claim.

## What the removal gave up

T-10-03 moved the rest of what `ddd-rust-domain` decides on to the native facts. The three items T-10-02 left on the tree-sitter side have moved:

- Which files make up the program. The `mod` walk in [`rust-modules.ts`](../../tools/ddd/lib/packaging/rust-modules.ts) now resolves modules from the native per-file declarations rather than from a tree-sitter module layout, and `moduleLayout()` is gone. The Cargo workspace scan and the layer assignment are read from `Cargo.toml` and were never a parser concern.
- Type resolution. [`program.ts`](../../tools/ddd/lib/rules/rust/program.ts) binds `impl` blocks to declarations and resolves a call's receiver type from the native facts; it imports nothing from the tree-sitter analyzer.
- Call sites. Rule `d` reads its calls, their receiver text and the forwarded-argument repository exception from the native `calls` and `forwarded_argument_calls` facts. The tree-sitter `value-flow.ts` that walked syntax nodes for the forwarding proof is deleted.

T-10-04 moved the last four declaration enumerations. `h` reads the native `impls` and the new `functions`, `l` reads the native `uses`, `m` reads the native `traits` and `types`, and `n` reads the native `constructions`, so every rule_id `ddd-rust-use-case` and `ddd-rust-interface-adapter` report now decides on the same batch — `i` already read the native `calls` with `program.receiver`, and `k` already read only the dependency edges `edges.ts` builds from the native `uses`. The protocol answers the two facts those enumerations had no native source for: the functions a file declares outside an impl block, and the line a type or trait declaration opens on.

T-10-06 removed the assets. Two answers were still coming from that parse, and each is now settled differently:

- **Whether a claimed file is inspected at all.** A claimed file was evaluated only if tree-sitter parsed it. It is now evaluated if the inspection can read it: `InspectionTarget` carries the claimed file's own path in place of a syntax tree, set where the read succeeds. A claim the read failed on still enters `targets`, so it is still a file the rules have to decide over and the extractor is still required for the run — it simply carries no declarations of its own, and the per-file rules report nothing for it. What the gate still reports about such a claim is whatever does not depend on reading it, such as sitting outside every module root.
- **Where a file's macro-opaque regions are.** The `analyzer.macro-opaque` notes are gone and nothing replaces them. Every shape that produced one is still covered on the native side except two: an expression-position macro (`let value = compute_amount!();`) and a non-built-in attribute macro (`#[my_attr]`). A verdict then said nothing at all about either, and the decision base was not shown to be complete without them. An attribute macro can replace the item it annotates — including the contents of an inline module, which it may rewrite into further declarations or a `mod` the walk never sees — so what the rules miss there is unresolved rather than empty. [#80](https://github.com/amadeus-dlc/aidlc-ddd-plugin/issues/80) has since settled the attribute macro: it is recorded as `domain-facts.unresolved` with the reason `attribute-macro`, and it stops the gates that decide rules `a` and `d` where those rules decide from it, as [how attribute macros are handled](#how-attribute-macros-are-handled) records. The expression-position macro is still reported by nobody. Adding a replacement note for it would be a new rule, which this change was not asked for. The shapes that stay covered are the item-position macro and the `cfg`/`cfg_attr` forms: refused as `domain-packaging.unresolved` on the declaration where they can hide a module, and noted as `domain-facts.unresolved` otherwise.

One thing the removal costs is a comparison, not a decision. Wherever an earlier task recorded "what the enumerations this replaced reported at this position is not established" — the positions under [which decisions moved](#which-decisions-moved) that the native declaration walk does not reach — the grammar that could have answered it shipped only as the vendored `tree-sitter-rust.wasm`. With that gone, those questions are not pending here; they are permanently unanswerable from this repository, and [completion tasks](completion-tasks.md) carries them to the parent issue on that basis.

One limit of the native answer is recorded rather than acted on: a derive macro can append items the parser never sees, but because it cannot change the members of the declaration it annotates, it is not recorded per occurrence. An attribute macro is acted on instead. It can replace the declaration it annotates, so the members after expansion cannot be determined from the declaration before it; the extractor records it, and a file rules `a` and `d` decide from that carries one stops the gates that decide them, as [how attribute macros are handled](#how-attribute-macros-are-handled) records. Item macros and `cfg`/`cfg_attr` are reported as `domain-packaging.unresolved` findings where they hide a module declaration, and as `domain-facts.unresolved` notes otherwise. On a run whose claimed files give these rules something to decide, a file the parser rejects is a note only while it is not among the ones the rules are decided from (the claimed files the gate inspects, plus every source of every program-layer crate); when it is among them the gate stops as inspection-impossible and reports the extractor's reason, because "this file declares nothing" is the one answer an unread file must not give.

## How attribute macros are handled

[#80](https://github.com/amadeus-dlc/aidlc-ddd-plugin/issues/80) decided this. An attribute macro (`#[tokio::main]`, `#[my_macro]`) replaces the item it annotates. After expansion the item can carry public fields or methods the source does not show, and an inline module can be rewritten into other declarations. A derive macro is different: it cannot change the item it annotates and can only add items beside it, and the helper attributes it declares (`#[serde(rename_all = "camelCase")]`) are inert — the derive reads them, and they expand to nothing. Syntax alone cannot tell a derive helper from an attribute macro of the same name, and helpers are common on domain structs, so the extractor decides as follows.

- **What is recorded.** An attribute that is neither built in nor an allow-listed helper of a derive on the same item is recorded as `unresolved` with the reason `attribute-macro`, on the line its `#` stands on. It travels the same path as `conditional-compilation`: it becomes a `domain-facts.unresolved: <file>:<line> attribute-macro` note, and the rule layer also reads it off the file's facts, as a line number rather than out of the note's text. The same spelling inside a `macro_rules!` body, a string literal or a comment declares nothing and is not recorded.
- **Built-in attributes.** These single-segment attributes are not recorded: `test`, `ignore`, `should_panic`, `derive`, `automatically_derived`, `macro_export`, `macro_use`, `proc_macro`, `proc_macro_derive`, `proc_macro_attribute`, `allow`, `expect`, `warn`, `deny`, `forbid`, `deprecated`, `must_use`, `link`, `link_name`, `link_ordinal`, `no_link`, `repr`, `crate_type`, `crate_name`, `no_main`, `export_name`, `link_section`, `no_mangle`, `used`, `inline`, `cold`, `naked`, `no_builtins`, `target_feature`, `track_caller`, `instruction_set`, `doc` (a doc comment included), `no_std`, `no_implicit_prelude`, `path`, `recursion_limit`, `type_length_limit`, `panic_handler`, `global_allocator`, `windows_subsystem`, `feature`, `non_exhaustive`, `debugger_visualizer`, `collapse_debuginfo` and `unsafe` (as in `#[unsafe(no_mangle)]`). Nor is any attribute under the tool namespaces `rustfmt::`, `clippy::` and `diagnostic::`. `cfg` and `cfg_attr` keep their own `conditional-compilation` record. What `cfg_attr` would apply is not read, because evaluating `cfg` is outside #80, so `#[cfg_attr(test, my_macro)]` is one `conditional-compilation` record and no `attribute-macro` record. Any other path-qualified attribute — `#[tokio::test]`, `#[async_trait::async_trait]`, even `#[core::prelude::v1::test]` — is recorded, because telling a crate's macro from a built-in re-exported under a path takes name resolution this protocol does not perform.
- **The allow list.** It lives in the extractor, as `DERIVE_HELPER_ALLOW_LIST` in [`domain_facts.rs`](../../experiments/rust-syn/src/domain_facts.rs), because deciding what to record is the extractor's part. Each row pairs a helper attribute with the derives that declare it, matched by the derive's last path segment, so `#[derive(Serialize)]` and `#[derive(serde::Serialize)]` both count. It holds two rows: `serde`, declared by `Serialize` and `Deserialize`, and `default`, declared by `Default` (the `#[default]` that picks the default variant of an enum). A helper is allowed only within the struct, enum or union whose own `#[derive(...)]` names one of the derives of its row: on that item, its fields, its variants and their fields. The same helper on an item without such a derive, on another item of the same file, or on an `impl` block of the same type — which is an item of its own — is recorded. A helper of any derive the list does not name, such as `#[error]` beside `#[derive(thiserror::Error)]`, is recorded.
- **Where it stops a gate.** `ddd-rust-domain`, which decides rules `a` and `d`, and `ddd-rust-use-case`, which decides rule `d`, stop as inspection-impossible — exit 127, no verdict, every record listed on stderr as `<file>:<line> attribute-macro` — when a file those rules decide from carries such a record. Those are the same files an unreadable file stops the gate for: the claimed files the gate inspects, plus every source of every program-layer crate. The file is the unit, so an attribute inside an inline `#[cfg(test)]` module of such a file (`#[tokio::test]`) stops the gate too, as does `#[async_trait]` on an impl block there. A file outside them — a `#[cfg(test)] mod tests;` file the module walk leaves out of the program, for example — keeps the record as a note, and the gate answers. When one of the files is unreadable as well, the gate reports the unreadable file, because it carries no declarations to judge at all.
- **Where it does not.** `ddd-rust-interface-adapter` decides neither rule `a` nor `d`, so every record is a note there and the gate answers. `ddd-rust-module-layout` and `ddd-check-rust-module-layout` read only the per-file declarations and are unchanged.

## Parsing does not resolve names or types

Syn documents its role as parsing Rust tokens into a syntax tree. `parse_file` accepts source text without an edition argument. Its modifiers and non-exhaustive/Verbatim nodes also require consumers to handle unsupported syntax explicitly. See the [syn API](https://docs.rs/syn/3.0.5/syn/), [parse_file](https://docs.rs/syn/3.0.5/syn/fn.parse_file.html), and [source-span support](https://docs.rs/proc-macro2/latest/proc_macro2/struct.Span.html).

The verifier demonstrates these boundaries with rustc:

- `MissingType` and a string returned from a function declared `-> u64` both parse; rustc rejects them. Parser success cannot satisfy type-dependent DDD rules.
- An aliased `Outcome<T>`, a re-exported error, and `Self::Error` retain useful syntax, but their target types remain unresolved. An application-defined `Result<T, E>` also parses; matching the spelling `Result` cannot establish the standard result/error contract.
- An inferred receiver call parses, but its receiver type remains unsupported.
- Identical `async fn` source parses for both trials; rustc rejects edition 2015 and accepts 2018. The simple struct control compiles in 2015/2018/2021/2024. This is an edition-boundary probe, not edition compatibility certification.
- Macro-generated fields are absent from unexpanded syntax. A field behind false `cfg` is present syntactically. The experiment reports both situations as unresolved, retaining field candidates without treating them as confirmed violations.
- Both `invoice.rs` and `invoice/mod.rs` containing `mod line;` report an external module requiring loading. The experiment does not discover child files or validate the project's module-layout setting.

Cargo workspace/target/feature discovery, imports and aliases across files/crates, generic substitution, trait resolution, macro expansion, and effective `cfg` selection remain separate responsibilities. Running `cargo check` establishes compiler acceptance but does not, by itself, deliver the resolved symbols required by custom DDD checks.

## A native executable is feasible on the tested host

The release binary was copied into a fresh temporary directory and executed with an empty PATH and no inherited environment. It needed neither Cargo/rustc nor Bun/tree-sitter at runtime. On the tested Apple Silicon Mac, the stripped executable was about 1.86 MB and linked only the system `libSystem.B.dylib`. Input hashes, exact versions, binary size/dependencies, timings, and per-case results are in the [execution evidence](evidence/rust-syn-spike.json).

Building this experiment requires the Rust toolchain and initially access to crates.io. The verifier additionally requires Bun. This does not add Rust as a requirement for current plugin users.

Before production distribution, decide supported OS/architecture targets, build/release binaries for each, verify checksums and executable permissions, test installation/update behavior, and define the missing-binary response. Avoid compiling source during sensor execution. A WASM build is another possible packaging choice; it was not attempted here. Linux, Windows, x86_64 and minimum OS/Rust versions are unverified. Plugin installation and gate integration are no longer on that list; [what this report has measured](#what-this-report-has-measured) records what replaced them.

## Reproduce and inspect the result

From the repository root:

```sh
cd ddd
bun run experiment:rust-syn
# Deliberately refresh the committed execution record:
bun run experiment:rust-syn --write
cargo fmt --manifest-path experiments/rust-syn/Cargo.toml --check
cargo clippy --locked --manifest-path experiments/rust-syn/Cargo.toml --all-targets -- -D warnings
```

The command builds with `--locked`, verifies the fixtures and real-sensor comparisons, runs rustc on compiler-oracle cases, checks relocation and deterministic output, and prints JSON. Any assertion failure exits nonzero. `SENSOR_EXPECTATIONS` in the verifier records what the gate answers for each case it also runs through the real sensor, and selects which of them those are. Update it for a production change that actually moves one, and this report with it.

The experimental executable accepts one JSON request on stdin. Protocol 1 below is the experiment's own; the sensors read the `domain-facts` protocol described in [native extractor distribution](native-extractor-distribution.md), never this one.

```json
{"protocol_version":1,"files":[{"path":"invoice.rs","source":"pub struct Invoice(pub u64);"}]}
```

It emits JSON with `field_inspection.state` (`pass`, `violation`, or `unresolved`), field candidates, syntax facts, and `semantic_analysis: "unsupported"`. `pass` applies only to this limited field inspection. Exit 0 means a report was produced, including unresolved reports; malformed requests exit 2 with stderr and no stdout. This is an experimental protocol, not the existing sensor verdict contract or the future shared schema. Syn nodes never cross the process boundary. There is no project-wide pass verdict.
