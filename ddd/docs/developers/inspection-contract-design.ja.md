# 共通検査契約とRustの参照解決設計

[English](inspection-contract-design.md) | 日本語 | [言語共通の設計](language-independent-design.ja.md)

状態: 2026-09-13の実装設計。Rust＋synの採用方針と共通原則は承認済み。本書はT-09の実装と両言語での検証への入力であり、本番アダプタ、スキーマ、移行の実装は未完了である。試作のJSON形式を公開契約として採用するものではない。

## 1. 言語の意味は各言語の実装内で扱う

Rustの構文解析にはRust実行ファイルとsynを使い、TypeScriptの構文・型解析にはCompiler APIを使う。DDDの要件、適用条件、必要な情報、判定の意味は共通の規則定義が所有する。言語別の実装が情報を抽出・解決し、共通の判定処理が正規モデルと実装写像に照らして検査する。承認・CI向けのアダプタは、プラグインの実行契約に従って結果を出力する。

```text
ソース＋プロジェクト設定＋コンパイラ・ビルドの証跡
             |
         言語別の実装
         Rust: syn＋参照解決
         TypeScript: Compiler API
             |
     バージョン付きの検査情報
             |
    正規モデル＋実装写像＋共通規則
             |
         規則ごとの検査結果
             |
         承認・CIアダプタ
```

図の上から下が処理順序になる。TypeScriptのラッパーでRustソースを再解析しない。synのノード、Cargoの構造体、Compiler APIのオブジェクトは、各言語の実装内に閉じる。アダプタが言語固有のコード形状を分類する際は、対応範囲内で根拠と完全性を示す。言語ごとに異なるDDD方針を決めることはしない。言語固有の詳細は診断用に保持できるが、共通規則の入力にはしない。

## 2. 検査情報を解析時の入力一式に結び付ける

解析スナップショットは、1回の検査に使ったソース・設定・モデルの組み合わせを識別する。ソース、マニフェスト、存在するロックファイルのハッシュ、写像・モデルの版、解析器・コンパイラのバージョン、選択したビルド設定を記録する。RustではCargoのパッケージ・ターゲット識別、ターゲットトリプル、feature、パッケージごとのedition、有効な条件付きコンパイルの根拠を含める。TypeScriptではtsconfigの継承・参照、コンパイラ設定、パッケージ識別・exports、解決条件を含める。異なるスナップショットの情報を混在させない。

解析範囲はルールごとに決める。ソースマニフェストは変更した成果物を示すが、依存・宣言の全体を表すものではない。必要なパッケージ、import、型、メソッド宣言を参照先まで読み込む。プロジェクト全体のモジュール配置検査は、引き続き所有する全パッケージ・ターゲットを調べる。必須の依存ソースや設定が欠けていれば検査不能であり、宣言が存在しない証拠にはならない。

キャッシュのキーには、関連するスナップショットと要求した情報の範囲を含める。内容ハッシュだけの構文キャッシュは各アダプタ内で使えるが、意味を解決した結果のキャッシュには流用しない。別名、feature、依存先、モデル、コンパイラの変更で、影響する結果を無効にする。

正規モデルの業務IDと、実装シンボルのIDを分ける。シンボルIDは内部形式を前提にしない識別子とし、同じスナップショットでは決定的に生成する。パッケージ・ターゲット・名前空間・宣言をまたいで一意にするが、ソース移動後の維持は要求しない。実装写像は業務IDを一意に解決したシンボルへ結び付け、変更後に再検証する。移行時に業務IDをコンパイラのIDやソース位置へ置換しない。

## 3. 解決状態と情報の完全性を明示する

要求した情報は、対象、情報の種類、スナップショット、根拠と、次の状態を持つ。

| 情報の状態 | 意味 | 利用側の扱い |
|---|---|---|
| `resolved` | 指定範囲で値と識別が確定している | 値と根拠を使う |
| `absent` | 関連範囲を完全に調べ、宣言・性質の不在を確認した | 規則が定める不在時の判定を適用する。不在自体が違反になる場合もある |
| `unresolved` | 入力不足、曖昧さ、未対応の意味、調査不足によって確定できない | 必須検査なら承認を止め、不足した入力・解析能力を示す |

一覧には`complete`または`partial`の網羅状態も付ける。不完全な空リストを、空の閉じた集合として扱わない。不完全な一覧から得た候補は診断材料にできるが、合格や「その要素は存在しない」という判定の根拠にはできない。他の必須項目が未解決でも、独立した根拠で確定した違反は保持する。

機械可読な理由と、ソース・設定上の場所を記録する。理由にはソース・設定不足、構文エラー、識別の曖昧さ、型・trait解決の未対応、未展開マクロ、条件付きコンパイルの不明、資源上限を含む。`unsupported`は解決できなかった理由であり、必須検査を任意に変える指定ではない。

## 4. パッケージ・型・操作・アクセスの情報を共有する

次の論理レコードを最初の契約とする。T-09でバージョン付きの直列化スキーマにし、プロセス境界の両側で検証する。

| レコード | 必須情報と制約 |
|---|---|
| パッケージ | パッケージ識別、所有するソースルート、実行ホスト・レイヤー・command/queryの分類、依存辺、完全性。版やターゲットを区別し、名前だけで識別しない |
| 型 | シンボル識別、所属パッケージ、宣言されたドメイン要素との写像、外部から観測できる状態の公開、生成・変更の根拠と対応限界。規則に必要な名前付き型の識別と構造上の違いを保持する |
| 操作 | シンボル識別、所属する型・パッケージ、正規コマンドまたは生成操作との写像、引数・戻り値の型識別、対象のコード形状・効果の根拠。生成メソッドも言語表現を問わず操作として扱う |
| 業務エラー契約 | 所属操作、識別済みの結果契約、成功・エラー型の識別、完全な閉じたエラー集合、コード上の各ケースと正規エラーIDの写像 |
| アクセス | 参照元と解決した参照先の識別、型だけの参照を含む依存種別、実際の入口、再公開経路、有効なアクセス可否。アクセス可否とレイヤーの許可を分ける |
| 検査根拠 | ソース位置、宣言・参照解決の経路、設定上の根拠、生成元・バージョン、スナップショット。所有ファイルはプロジェクト相対パス、外部入力は依存先の識別と相対パスで表す |

行番号は1始まりとする。RustのspanとTypeScriptの位置情報で文字の数え方を揃えずに、列番号を比較しない。最初の承認出力はファイル・行を維持できる。詳細な位置情報を直列化する際は、文字の数え方を一つに定め、Unicode・CRLFを試験する。

公開対象の一覧はコードとパッケージ情報から導出する。全exportを利用者が二重管理する成果物を追加しない。別名の参照先が許可された型であっても、通った経路が正当とは限らない。内部パスへの迂回、禁止レイヤーへの依存、禁止されたワイルドカード公開は、それぞれ検査する。

## 5. Rustの明示的な宣言・参照を根拠付きで解決する

### Cargoの実行条件を揃える

`cargo metadata --format-version 1`に、プロジェクトが選んだプラットフォームとfeatureの条件を渡す。パッケージ・ターゲット・依存先の識別と、名前を変更した依存関係を取得する。`resolve`のグラフとパッケージ宣言は役割が異なるため、未絞込みのパッケージ一覧を有効な依存グラフとして扱わない。推移的な依存や名前変更の解決が必要なら`--no-deps`では不足する。通常・build・devの依存種別と、ホスト・ターゲットの条件を保持し、一つのアプリケーション層グラフへ混ぜない。[Cargo metadata](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html)を参照。

検査は準備済みの依存とコンパイラ・ビルドの証跡を使い、ロックファイルを変更しない。センサーではfrozen条件のmetadataを利用でき、準備不足は検査不能として報告する。依存の準備と`cargo check`は明示的なビルド・検証経路で行い、センサーのたびに暗黙のコンパイルを実行しない。同じ条件のコンパイラ診断と有効なビルド設定を記録する。`cargo check`にはビルドスクリプトや手続きマクロの実行が伴うため、検査に関係する生成ソース・設定も把握する。成功しても、独自規則に必要な解決済みシンボルのグラフが得られるわけではない。[Cargo check](https://doc.rust-lang.org/cargo/commands/cargo-check.html)を参照。

解析しやすくするために`--all-features`へ切り替えない。featureやターゲットが異なる場合は、スナップショットと結果も分ける。コンパイラが受理した証拠が欠ける場合、影響するedition・型依存の検査は未解決とする。局所的な構文の根拠は引き続き報告できる。

### 宣言と明示的な参照の索引を作る

synから宣言、構造化されたパス・型、位置、属性、モジュール、impl、シグネチャを取得する。外部モジュールは実際の宣言から読み込み、確認済みのパス・設定と、選択した両モジュール配置に従う。`crate`・`self`・`super`、明示的なimport、名前変更した依存、再公開、型別名を、名前空間とスコープを持つシンボル表で解決する。シャドーイング、raw識別子、可視性、アクセス経路を保持する。循環・曖昧さを検出し、最初に見つかった同名宣言を採用しない。Rustは名前空間を区別し、型に依存する解決段階も持つため、単純な名前表だけでは扱えない。[Rustの名前解決](https://doc.rust-lang.org/reference/names/name-resolution.html)を参照。

初期実装は明示的な型参照と元の型をたどれる型別名を解決し、対応する型・ライフタイム・const引数を構造に沿って置換する。未対応の置換は未解決とし、型引数を削って一致させない。inherent impl内の具体的な`Self`は所属型から解決する。明示された引数・ローカル変数・フィールドの型は、スコープと識別を確定できる場合に結び付ける。inherent関数の既知の戻り値も、呼出し先と必要な引数置換を確定できる場合に限り追跡する。これは範囲を限定した参照解決であり、式全般の型推論ではない。

シンボルを解決済みと報告する前に、関連する条件分岐、glob import、生成宣言によって競合する候補が増えないことを確認する。未解決マクロがあっても、無関係で完全なフィールド情報まで無効にする必要はない。ただし、そのマクロが完全性を変え得る名前や集合は未解決にする。影響範囲を狭く証明できるまでは広めに承認を止めてもよいが、マクロの影響がないと暗黙に仮定してはならない。

### 構文対応と意味の解決能力を分ける

式全般の型推論、traitの実装選択、関連型の解決、独自deref・型強制、マクロ展開はsynが提供する機能ではない。これらが必要な必須情報は、別途検証した意味解析の実装が同じスナップショットで供給するまで未解決とする。syn採用に伴ってrustc-private・nightly APIやrust-analyzer内部APIを暗黙に追加しない。採用するには、互換性と配布の検証が別途必要になる。T-09では明示的に対応するケースを成立させ、通常の想定利用でも承認を止めてしまうケースを洗い出す。それがリリースに必要なケースなら、規則の例外で逃げず、意味解析の実装をリリースの前提作業に加える。

editionとファイル配置は独立している。synの解析成功を、そのパッケージのeditionでコンパイラが受理する証拠にしない。[試作](rust-syn-spike.ja.md)はこの違いを再現し、公開タプルフィールドと明示的なreturnを持つgetterを回帰検査へ追加する必要性も示した。

## 6. 操作のエラー契約を解決してから集合を比較する

コマンド・生成操作の各写像について、次の順に検査する。

1. 操作を一意に解決し、所属するドメイン要素と正規操作の写像を検証する。
2. 戻り値の型と意図した結果契約を解決する。Rustの型別名は標準Resultの識別までたどり、アプリ独自の同名型は区別する。TypeScriptは設定した言語拡張用Resultの定義・構造を解決する。`any`・`unknown`・型アサーション・広すぎる型で、必要な閉じた契約の根拠を代用しない。特定の外部Resultライブラリは、この設計でも選ばない。
3. エラー型を解決し、完全な閉じたケース集合を取得する。型別名、型引数、条件付きバリアント、関連型の解決責務を残す。開いた集合や不完全な集合は未解決であり、空集合として扱わない。
4. コード上の各ケースを正規エラーIDへ結び付ける。正規エラーが宣言する所属と、そのエラーを含む操作の両方が一致することを確認する。各操作は自身のエラー契約を持ち、他の操作に属するエラーを含む広いunionは違反とする。
5. 要求された集合と観測した集合を比較し、不足・余分・所属違いを検出する。完全な情報による不一致は違反、型・集合の根拠不足は検査不能とする。生成メソッドにも同じ判定を適用する。

型とケースの一致だけでは、各失敗経路の状態維持や不変条件を証明できない。TypeScriptの可変参照の分離、Rustの明示的な共有・内部可変性も含め、生成アプリケーションの振る舞いテストと意味のレビューを維持する。

## 7. 実行失敗と規則の判定を分ける

解析器の実行状態は`completed`・`unavailable`・`failed`とする。実行完了時は、要求した規則・対象・設定の組み合わせごとに結果を返す。判定は`pass`・`violation`・`unresolved`・`not-applicable`とし、根拠となる情報を参照する。適用外には範囲・適用条件の証明が必要で、モデル不足や解析未対応を理由に選べない。

承認できるのは、必須結果がすべて合格または根拠のある適用外で、必要範囲の調査が完全な場合に限る。違反と検査不能はともに承認を止めるが、後者をアプリケーションのDDD違反として報告しない。他の検査が未解決でも、確定した違反は保持する。結果不足、未知バージョン、古いスナップショット、途中までの出力、クラッシュ、タイムアウト、不正な応答も承認を止める。

現行センサーの単一JSON判定と、確定した違反の既存rule IDを維持する。ラッパーは未解決結果を明示的なブロッキング診断へ変換し、ツール利用不能・時間超過の既存の扱いも維持する。ネイティブ実行ファイルの終了コード0だけで承認しない。CIも同じ必須結果を判定し、承認不能なら非ゼロで終了する。試作のプロセス間形式はバージョン付きアダプタを通じて置き換え、承認経路へ直結しない。第三者のフレームワーク実装は変更しない。

## 8. 移行前に両言語の対応ケースで契約を試す

| シナリオ | Rustの入力 | TypeScriptの入力 | 必須の結果 |
|---|---|---|---|
| 意図した状態隠蔽 | 名前付き・タプル構造体の非公開フィールド | classの`#`フィールドとコンパニオンのクロージャ | 対応範囲の根拠を解決し、公開違反なし |
| 状態の公開 | 名前付き・タプルの`pub`と制限付き公開 | 公開状態と、対応パターン内の可変参照の漏出 | 公開を証明できれば違反、それ以外は検査不能 |
| 別名経由のエラー戻り値 | 明示・完全修飾Result、import名変更、再公開、ジェネリック別名 | プロジェクト設定に従う結果・エラー型のimport・再公開 | 同じ操作・エラー識別と完全な集合を取得 |
| 結果型の誤識別 | ローカルの同名`Result` | 無関係な似た構造の結果型や検査を回避する型 | 名前だけでは合格しない |
| エラー不一致 | enumバリアントの不足・余分・所属違い | 閉じたunionの要素の不足・余分・所属違い | 同等の違反。不完全な集合は検査不能 |
| 生成時エラー | 自身のエラーを返す検証付きcreate | classのfactoryとコンパニオンのcreate | 同じ所属・集合の検査 |
| 公開経路の迂回 | 内部パスや禁止レイヤーからの参照 | 相対・内部パスや禁止レイヤーからの参照 | アクセス可否と依存方向を独立して検査 |
| 解決の限界 | マクロ・不明なcfg、曖昧な別名、推論を要するtraitレシーバー | 未解決import、不正なプロジェクト参照、未対応の戻り値契約 | 必須検査なら理由を示して承認停止 |
| 設定変更 | feature・ターゲット・edition・配置の変更 | tsconfig・exports・配置・表現の変更 | 影響する情報を再計算し、古い判定を流用しない |
| ホストと業務ソースの境界 | Cargoのアプリ・workerホストとドメインパッケージ | Next.jsサーバーホストとドメインパッケージ | 同じ依存方向と業務責務の配置 |

循環、パッケージの同名・複数版、不完全な一覧、バイナリ欠落、不正応答、Unicodeの位置情報、移行の再実行も契約テストへ含める。既存の全センサー、配布、導入、承認、実アプリケーションの振る舞い検証は、T-10/T-11の完了条件として維持する。

T-09は直列化・バージョン設計、検証、共通判定、限定したRust/TypeScript検証、明示的な成果物移行を担当する。T-10は本番Rust実行ファイル、全規則の移行、タプル・getterの回帰検査、対応環境のネイティブ配布、接続を担当する。T-11はTypeScriptの全面対応を担当する。厳密なスキーマバージョン、配布対象、より深いRust意味解析の実装は、証跡を要する実装・リリース判断として残す。本書の記載を実装済みとは扱わない。
