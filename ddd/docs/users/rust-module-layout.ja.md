# Rustモジュールの配置契約

[English](rust-module-layout.md) | 日本語 | [利用者向け文書](README.ja.md)

アプリケーションのプロジェクト直下、`aidlc/` と同じ階層の `.ddd.toml` で配置形式を選びます。設定は、配下のCargoパッケージすべてに適用します。入れ子のプロジェクト、すべての層、テストコードも対象です。Rustプロジェクトで設定がなければ承認を止めます。既存ファイルからチームの選択を推測しません。

```toml
schema_version = 1
[rust]
module_layout = "file"
```

指定できる値は `file` と `mod-rs` です。未知のキー、下位ディレクトリの設定ファイル、クレート別の上書き、`mixed` は拒否します。新規プロジェクトには `file` を推奨します。設定を切り替える際は、検査対象のプロジェクト全体を新しい規約へ揃えてください。

| モード | 親モジュール | 末端モジュール |
|---|---|---|
| `file` | `src/invoice.rs` | `src/invoice/line.rs` |
| `mod-rs` | `src/invoice/mod.rs` | `src/invoice/line.rs` |

親とは、内部にモジュール宣言を持つ外部ファイルのモジュールです。インラインやテスト専用の子も含みます。`mod-rs` でも末端はモジュール名のファイルとし、すべての末端をmod.rsに置く形式にはしません。lib.rs・main.rsや明示したターゲットパスなど、Cargoターゲットのルートはその名前を維持します。インラインモジュールを外部ファイルに分ける必要はありません。`#[path]` で配置先を変えても、実ファイル名は選択した規約とモジュール名に従います。

このモードはファイル配置の方針です。RustのeditionはCargo.tomlで管理します。検査はeditionで配置の判定を切り替えず、editionごとの名前解決を完全に保証するものでもありません。Rust自体は両形式を受け付けますが、このプラグインではレビューの一貫性を保つため、チームが選んだ形式へ統一します。[Rust公式仕様](https://doc.rust-lang.org/reference/items/modules.html#module-source-filenames)も参照してください。

## 検査対象

プロジェクト配下のCargoマニフェストとRustファイルを列挙し、Cargoターゲットからモジュール宣言をたどります。lib・bin・test・example・bench・build-scriptを対象とし、層、ドメインモデルの実行状態、source-manifestの申告には依存しません。名前変更や削除の後に古いファイルが残らないよう、未登録のRustファイルも報告します。

隠しファイル・隠しディレクトリと、aidlc・node_modules・vendor・target・distは探索対象外です。外部依存や生成物はこれらの場所に置き、アプリケーションが所有するソースを検査範囲の外へ置かないでください。検査対象のモジュールから参照したファイルは、引き続き解決と配置検査の対象です。シンボリックリンク、クレート外への参照、曖昧・欠落したファイル、cfg_attrによるパス切り替え、構文エラー、モジュールを生成し得るitem macroは検査済みとして通しません。条件付きコンパイルは評価せず、テスト専用を含む宣言上の構造を検査します。未対応の構成は、この検査の導入前に解消してください。

## 承認とCI

blockingセンサー `ddd-rust-module-layout` は、次の通常承認で実行します。

| ステージ | 発火する成果物 |
|---|---|
| code-generation | code-summary.md |
| build-and-test | build-and-test-summary.md |
| ci-pipeline | quality-gates.md |

CIでは、導入済みのコマンドにアプリケーションのプロジェクトルートを渡します。作業ディレクトリは問いません。

```sh
bun /path/to/project/.codex/tools/ddd-check-rust-module-layout.ts --project /path/to/project
```

Claude Codeでは `.claude/tools/` を使います。CIにはBunと導入済みのDDDツールを用意してください。コマンドはJSONを出力し、1つ以上のCargoパッケージを検査して所見がなかった場合だけ終了コード0を返します。引数不正、解析不能、検査パッケージ0件、規約違反では非0を返します。センサーの実行ファイルはフレームワークのJSON判定規約を使うため、CIコマンドの代用にはしません。

Cargo.toml・設定だけの変更、名前変更、削除を含め、毎回実行してください。変更・申告されたRustファイルによる絞り込みはしません。cargo checkとアプリケーションのテストも併用します。CIステージへの追加指示は、このコマンドを必須検査としてパイプラインに組み込ませます。プラグインの導入だけで外部CIサービスが設定されるわけではありません。

単独ステージでは、同じコマンドの成功を確認してから完了を報告します。標準AI-DLC 2.8.2は単独完了時の一般センサーを強制しません。通常承認への登録だけでは、このフレームワークの制約は解消しません。

## 所見と移行

| 規則 | 対処 |
|---|---|
| module-layout.configuration | プロジェクト直下に有効な設定を1つ置き、競合する設定を解消する。 |
| module-layout.violation | 所見が示すパスへ移動し、子の解決先を維持しながら宣言を更新する。 |
| module-layout.unresolved | モジュールの欠落・曖昧さ、未対応構造、未登録ソース、Cargoの探索上の問題を解消する。 |

親を `invoice/mod.rs` から `invoice.rs` へ移すとき、子は `invoice/` 配下に残します。明示したpath属性は相対パスの基準が変わり得るため、確認してください。通常のmod宣言では新旧のファイルを共存させず、古いファイルを削除します。移動後に配置検査・コンパイル・テストを実行します。検査を通すために、利用者のコードを無断で移動したり、選択した配置方針を書き換えたりしません。

正常・違反・境界ケースは[検査対応表](../developers/sensor-coverage.ja.md)を参照してください。
