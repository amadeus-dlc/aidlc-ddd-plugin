# プロジェクトのDDD成果物一式を移行する

[English](artifact-migration.md) | 日本語 | [利用者向け文書](README.ja.md)

`ddd-artifact-set migrate` は、1つのプロジェクトのDDD成果物を1回の明示的な操作でまとめて変換します。対象は、プロジェクト設定と、1つのintent記録が持つ正規モデル・実装写像・すべてのレイヤー宣言です。各成果物には個別の移行コマンドもありますが、個別コマンドどうしは互いを検査できません。写像と宣言は正規モデルに対して読まれるため、モデルが移行前のままの状態で1件ずつ変換すると、これから変わるモデルに対して変換することになります。このコマンドは、これから書き込むモデルに対して一式を評価し、すべての部分が準備できるまで何も書き込みません。

## 一式が含むもの

| 成果物 | 場所 | 参照 |
|---|---|---|
| プロジェクト設定 | `<project>/.ddd.toml` | [プロジェクト設定](project-settings.ja.md) |
| 正規モデル | `<record>/inception/ddd-domain-modeling/ddd-domain-model-yaml.md` | [操作ごとのエラー](domain-model-operation-errors.ja.md) |
| 実装写像 | `<record>/inception/domain-design/ddd-aggregate-mapping.md` | [実装写像](implementation-mapping.ja.md) |
| レイヤー宣言 | `<record>/construction/[<unit>/]infrastructure-design/cicd-pipeline.md` の `## DDD Layer Structure` 節（すべて） | [レイヤー宣言](layer-declaration.ja.md) |

写像を持たない記録は、写像なしのまま変換します。記録が持っていない成果物を作ることはありません。レイヤー宣言は Unit ごとに1つ、デリバリー計画が Unit を作らなかった場合はステージ直下に1つ置かれます。どちらも登録された場所であり、どちらも変換します。

## 実行する

```sh
bun <project>/<harness-dir>/tools/ddd-artifact-set.ts migrate \
  --project <プロジェクトroot> \
  --record <intent記録> \
  --supplement <写像の補足YAML> \
  [--apply]
```

`--apply` を付けなければ何も書き込みません。変換する内容を報告するだけです。`--record` は `aidlc-state.md` を持ち、かつ `--project` の内側にあるディレクトリを指す必要があります。このコマンドが変換する設定は、そのプロジェクトのものだからです。

`--supplement` は、crate/module 形式の写像に書く場所がない情報を渡すファイルです。各集約の型名と、各コマンド・各ファクトリ規則のメソッド・エラー型・エラーケースが該当します。形式は[crate/module 形式の写像を移行する](implementation-mapping.ja.md)を参照してください。すでに現在の形式になっている写像に補足は不要なので、写像の変換後はこのオプションを省略できます。

## 報告の内容

コマンドは標準出力にJSONの報告を1つ書きます。

| 欄 | 意味 |
|---|---|
| `outcome` | 一式全体の結果 |
| `artifacts[]` | 成果物ごとに1件。`artifact`、`path`、`outcome` と、その結果が持つ内容 |
| `findings` | 成果物を読む前に要求そのものを拒否した場合にだけ現れる |

一式の結果は、成果物の結果から1つの規則で選びます。拒否が、まだ不足している情報より優先し、それが変換すべきものがあることより優先し、それが残っていないことより優先します。存在しない成果物は何も決めません。

| `outcome` | 終了コード | 意味 |
|---|---|---|
| `candidate` | 0 | すべての成果物を変換できる。`--apply` がないため何も書いていない |
| `applied` | 0 | 変換すべきものがあった成果物をすべて変換した |
| `already-migrated` | 0 | 変換すべきものが残っていない |
| `missing-information` | `--apply` なしで0、ありで1 | 現在の形式が必要とする情報がまだ述べられていない。何も書いていない |
| `rejected` | 1 | 拒否があった。何も書いていない |
| `write-failed` | 3 | 書込が途中で失敗した（下記参照） |
| `invalid-arguments` | 2 | コマンドラインを拒否した。何も読まず、何も書いていない |

成果物ごとの結果は `absent`、`candidate`、`already-migrated`、`applied`、`missing-information`、`rejected`、`write-failed` のいずれかです。

## 書き込む前に何を検査するか

まず一式全体を評価します。写像と宣言は、ディスク上のモデルではなく、この実行がこれから書き込む正規モデルに対して検査します。そのため、ある成果物が別の成果物の定義しない要素を参照している場合、半分だけ変換された記録に持ち越されずに、その場で報告されます。

ファクトリ規則の業務エラーを記録する場所がないモデルも、他の成果物が名指ししているモデルであることに変わりはありません。モデル自身は不足を報告しつつ、写像と宣言は、その形式が述べる内容に対して検査します。これらは別々の成果物であり、それぞれの結果を持ちます。一式の結果は、上記の1つの規則をすべての成果物に適用したものです。

この場合は2巡することを見込んでください。モデルの業務エラー不足を報告する実行では、写像はその業務エラーを持たないモデルに対して検査されるため、`candidate` になり得ます。業務エラーを補って一式を再実行すると、写像はそれらに対して検査され、まだ写像していないエラーケースを写像自身の `missing-information` として報告することがあります。つまり、1巡目で準備できていた写像が2巡目もそのままとは限りません。これは写像が勝手に変わったのではなく、モデルに写像すべき操作が増えたためです。

いずれかの成果物が拒否されるか情報不足の場合、どのファイルも変わりません。準備できていた成果物も書きません。

## 書込が途中で失敗した場合

失敗した書込を成功として報告することはなく、巻き戻しもしません。巻き戻し自体が失敗しうるため、誰も名指しできない状態になるからです。報告は、どこで止まったかをそのまま示します。

| 欄 | 意味 |
|---|---|
| `written` | 失敗前に書き込んだ成果物 |
| `failed` | 書込が失敗した成果物と、その理由の `detail` |
| `pending` | まだ変換していない成果物（書き込む順） |
| `rerun` | 何を解消すればよいか、再実行すると何が起きるか |

書込を止めた原因を解消して、同じコマンドを再実行してください。すでに書き込んだ成果物は `already-migrated` として読まれ、残りが変換されるので、同じ記録の上で一式が完了します。

一式は1つの順序で書きます。正規モデル、それを名指しする写像、パス順のレイヤー宣言、最後にプロジェクト設定です。設定はプロジェクト全体を構成する唯一の文書だからです。

## 移行が保つもの

変換は構造的に行い、文字列置換は行いません。業務ID、参照、業務上の記述、そして記述された言語はそのまま引き継がれます。値の文言がたまたま旧形式のキーと同じ字面を含む場合も同様です。各成果物のラベル付きYAMLブロック1つの外側は変わりません。本文、節の見出し、フェンス記号、その他のフェンス付きブロックはバイト単位で保たれるので、宣言の隣にあるCI設定はそのまま残ります。

変換済みの一式に対して再実行すると `already-migrated` を報告し、1バイトも変更しません。
