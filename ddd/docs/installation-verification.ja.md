# 導入・更新の検証

[English](installation-verification.md) | 日本語

対象は標準AI-DLCを導入済みのClaude CodeとCodex。確認環境はAI-DLC 2.8.2、Bun 1.3.13。

## 自動実行するコマンド

```sh
cd ddd
bun run test:install
bun run test:install:remote
```

前者はヘルパーの検査と、使い捨てプロジェクトに対するインストーラCLIの検査を行う。後者は実際のGitHub mainアーカイブを取得する2件を有効にする。通常のサンドボックスにはtest:installを含め、ネットワーク検証は任意実行とする。

| 検証 | 結果 |
|---|---|
| ヘルパーとローカルCLI | 45成功、ネットワーク検証2件はskip |
| GitHub mainの実取得と導入 | 両環境で成功 |
| プラグイン検証・整形 | 成功 |

CLIでは、新規導入、再導入、配布ファイル更新、contributionのみの更新、新規・更新のdry-run、compose失敗、不正なcontribution、所有権の衝突、配布対象から外れたファイル、旧形式の記録、固定タグの整合性、対象外環境、競合する取得指定、ビルド済み配布物、導入先のシンボリックリンクを検査する。導入されたセンサーを実行し、ステージのグラフ登録も確認する。

tag/latestの取得はHTTP境界にアーカイブfixtureを用い、バージョン不一致とHTTP失敗も確認した。公開タグの作成・実導入は行っていない。実際のモデルによるステージ実行と、モデルへのルール到達は別の検証である。

## 導入先への反映

配布物をビルドし、対象ハーネス・共有スキル・AI-DLC記録の候補コピーを作る。配布物の標準hookでcomposeし、drop、グラフのコンパイル、選択した配布物と配置されたファイルの一致を確認してから反映する。dry-runは反映前に終了する。

反映するのは変更ファイルだけ。候補作成時と導入先の内容を照合し、シンボリックリンク経由の書込みは拒否する。反映用のバックアップも保持する。compose・検証の失敗時は導入先を変更しない。反映中のプロセス強制終了やストレージ障害は注入しておらず、ファイルシステム全体の原子性を保証するものではない。

導入ロックでインストーラの同時反映を防ぐ。反映中に捕捉した失敗では以前の内容への復元を試み、復元自体が失敗した場合は回復用ディレクトリをエラーに表示する。

## 所有権と更新記録

記録は `<harness>/tools/data/ddd-install.json` に置く。バージョン、取得元、日時、配布ファイルのダイジェスト、contributionを含む配布物全体のダイジェスト、ファイルごとの所有権ハッシュを記録する。バイナリはバイト列のままハッシュ化する。

更新するのは記録済みで未編集のプラグインファイルだけとし、配布されなくなった記録済みファイルも削除する。未所有ファイルとの衝突や利用者の編集は上書きせず報告する。旧形式の記録は、以前の配布ファイルのダイジェストを検証できれば所有権情報を追加できる。検証できない場合は、記録された取得元バージョンで所有権を確立してから更新する。

`--update` は記録した取得元を再利用する。固定タグでは記録したファイルを確認し、正常なら変更なしとする。`--skip-build` は既存のビルド済み配布物を使用する。取得元を明示する場合は、--from、--ref、--tagのいずれか1つを指定する。
