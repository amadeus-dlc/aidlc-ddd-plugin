## Q1: 共通情報の検証と状態公開の判定を、誰が所有するか

次の二つの処理を、同じ構成要素が所有するかを確認する。

- Rust／TypeScriptから受け取った情報について、形式の版、入力との対応、完全性を検証する。
- 検証した情報から、状態公開の正常・違反・検査不能を判定する。

どちらの案でも、言語ごとの根拠抽出は共通判定から分離する。検証処理と判定処理には別々の関数・試験を設け、未検証の情報を直接判定へ渡さない。今回扱う情報形式は状態公開に必要なものだけとする。

- A. 「状態公開検査」が情報契約・検証・判定をまとめて所有する（推奨）。Rustの根拠抽出、TypeScriptの根拠抽出、検証実行と合わせて四つの構成要素とする。一規則に必要な情報と判定を一緒に変更できる。別規則が増えて独立した変更理由が生じた時点で分割できる。
- B. 「状態公開の証跡」と「状態公開の判定」を別々の構成要素にする。全体は五つになる。情報契約の所有者を独立させられる一方、この一規則でも変更と試験を二つの境界にまたがって調整する必要がある。

## Consolidated Summary Confirmation

- Q1はAとする。状態公開に必要な共通情報の契約・検証・判定を「状態公開検査」がまとめて所有し、内部の関数と試験は分ける。
- 論理的な構成要素は四つとする。「状態公開検査」（StateExposureInspection）、「Rustの状態公開根拠」（RustStateEvidence）、「TypeScriptの状態公開根拠」（TypeScriptStateEvidence）、「状態公開の検証実行」（StateExposureVerification）である。
- 状態公開検査は、入力・設定・対象との対応、情報の完全性、根拠の妥当性を確認してから規則を判定する。共通形式と規則結果の意味を所有し、AST、Cargo構造体、Compiler APIの型には依存しない。
- RustとTypeScriptの根拠抽出は、それぞれの解析器固有の情報と、指定型から共通形式への変換を所有する。構文上の候補と確定した根拠を区別し、対応できない範囲を未解決として伝える。
- 検証実行は、固定入力、期待値、実行記録を所有する。入力と解析設定を確定し、指定言語の抽出処理と共通の状態公開検査を呼び、実行結果を期待値と比較して報告する。言語別抽出と共通判定は、検証実行へ逆依存しない。
- 共通の検査要求・証跡・判定結果と、解析器内部の構文情報、検証ケース・実行記録について、所有者を一つずつ定める。境界を越える際は契約に従って受け渡し、他の構成要素の内部状態を直接共有しない。属性名と識別の役割まで整理し、具体的なデータ型・検証条件・多重度は後続設計で定める。
- 入力不足、不正応答、実行不能を正常へ変換しない。未解決事項があれば全体は検査不能とし、独立に確定した違反と未解決理由を両方保持する。
- Rustは名前付き・タプル構造体、TypeScriptはclass・構造体＋同名コンパニオンという承認済みの表現を扱う。既存Rustセンサーの入口と出力契約を維持し、新経路と回帰試験で比較する。
- コンポーネント一覧・所有関係・依存図をcomponents.md、分割案の選択理由と不採用案をdecisions.md、承認済みの機能要件との対応をtraceability.jsonへ記録する。共通判定を独立に検証できることと再現性も、責務と試験境界へ対応付ける。
- ファイル配置や公開APIの詳細、パッケージ探索、一般の型解決、成果物・設定移行、本番センサー切替、ネイティブ配布、Webフレームワーク統合を、この段階の設計へ追加しない。
