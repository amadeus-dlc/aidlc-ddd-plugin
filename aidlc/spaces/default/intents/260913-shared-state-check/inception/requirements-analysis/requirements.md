# 状態公開の共通検査 — 要件

## Intent Analysis

[Issue #38](https://github.com/amadeus-dlc/aidlc-ddd-plugin/issues/38)を一つのintentとして扱う。指定したドメイン型について、RustとTypeScriptで同じ意味の状態公開規則を判定し、開発者とレビュー担当者が結果と根拠を再現できる最小経路を作る。

今回の規則は、ドメイン型が保持する状態を直接公開しないことである。公開されたデータメンバーは、読み取り専用であっても状態公開に含む。状態を隠した型の操作メソッドや、そのメソッド固有の振る舞いまで一括して証明する規則にはしない。対応するソース形状を明示し、その形状では判断できない入力を正常として通さない。

変更の種類は、既存Rust検査の改善を伴う共通判定経路の追加である。対象は`ddd/`内の開発用検証経路であり、深度はStandardとする。親課題[#34](https://github.com/amadeus-dlc/aidlc-ddd-plugin/issues/34)の型解決・移行・本番統合全体を、このintentの終了条件へ取り込まない。

## Functional Requirements

### FR1: 明示された入力と検査対象を同定する

固定プロジェクト入力から、指定されたソース、型、言語、解析設定の組み合わせを検査する。ワークスペースを探索して対象を推測しない。

- **FR1.1**: 要求と応答を、入力内容・設定・対象の識別で対応付ける。ソースまたは判定に関係する設定が変わった場合、以前の応答を同じ要求の根拠として採用しない。
- **FR1.2**: 対象が見つからない、同名候補が複数あり区別できない、または指定した型の情報が返らない場合は検査不能とし、対象と理由を報告する。別の型の結果で代用しない。

受入条件: 一意に特定できる型を指定するとその型だけの結果を得る。対象を削除・曖昧化した入力、識別が異なる応答、結果が欠けた応答は、いずれも正常にならない。

根拠: Issue #38、要件確認、business-overview.md。

### FR2: Rustの状態公開情報を抽出する

既存のRust＋syn試作を利用し、名前付き構造体とタプル構造体の対応形状から、状態公開の根拠を共通形式へ変換する。

- **FR2.1**: 非公開フィールドを公開違反として報告しない。`pub`、`pub(crate)`などの制限付き公開を含む非privateフィールドは、名前付き・タプルの両形式で状態公開として報告する。
- **FR2.2**: 構文エラーや、条件付きコンパイルなどによって対象・フィールドの成立を確定できない箇所を明示する。構文上の候補だけで確定違反を作らず、独立した根拠のある違反は保持する。

受入条件: 名前付き・タプルごとに非公開、`pub`、`pub(crate)`の固定入力を実行し、非公開は正常、公開は違反となる。解釈できない条件を持つ入力は検査不能となる。構文解析の成功や試作プロセスの終了コード0だけで正常と判定しない。

根拠: Issue #38、architecture.md、共通検査契約。

### FR3: TypeScriptの状態公開情報を抽出する

TypeScript Compiler APIの`Program`と`TypeChecker`を使い、合意済みの二つの表現から状態公開の根拠を共通形式へ変換する。採用したAPI版を記録する。

- **FR3.1**: class形式では、`#`フィールドに状態を保持する代表例と、公開データメンバーを持つ代表例を扱う。
- **FR3.2**: 構造体＋同名コンパニオン形式では、インスタンスメソッドを返却オブジェクト内に置き、状態をクロージャに隠し、非公開の`unique symbol`でブランドを付ける代表例を扱う。返却オブジェクトに状態を直接公開する代表例も扱う。
- **FR3.3**: 単一ファイルの対応形状では判定できない入力は、未解決の対象・範囲・理由を返す。例えば継承、spread、計算されたメンバー名、型アサーション等を、根拠なしに安全な形状として扱わない。これらをすべて対応させる要件ではなく、採用する対応範囲と検査不能の境界を設計・試験で固定する。

受入条件: 両表現で、状態を隠す代表例は正常、状態を直接公開する代表例は違反となる。対応範囲外の代表例は検査不能となる。ブランド用の印や操作メソッドの存在だけを状態公開の違反にしない。

根拠: Issue #38、要件確認、言語共通の設計、共通検査契約。

### FR4: 一規則に必要な共通情報を検証する

言語別抽出処理と共通判定処理の間に、状態公開の一規則だけに必要な、版を持つ情報契約を置く。

- **FR4.1**: 情報の`resolved`／`absent`／`unresolved`と、一覧の`complete`／`partial`を区別する。`absent`は必要な範囲を確認して不在を証明できた場合だけに用いる。不完全な空リストは不在の証明にしない。
- **FR4.2**: 対象・入力・設定の識別と、情報の根拠を共通判定まで保持する。共通契約と共通判定は、言語固有のAST、Cargo構造体、Compiler APIの型を受け取らない。
- **FR4.3**: 未知バージョン、不正形式、欠落した必須情報、要求と一致しない識別を検出し、未検証の応答を判定根拠にしない。情報不足や実行失敗が、空の所見リストへの変換によって正常になる経路を作らない。

受入条件: 同じ意味の検証済み情報を渡すと、言語にかかわらず共通判定が同じ結果を返す。部分的な空集合、未知版、壊れた応答、欠落・不一致を与える契約試験は、すべて正常を拒否し、理由を残す。

根拠: Issue #38、要件確認、architecture.md、共通検査契約。

### FR5: 正常・違反・検査不能を根拠付きで判定する

解析器の実行状態`completed`／`unavailable`／`failed`と、規則の結果を別々に表す。実行完了は規則への合格を意味しない。今回の明示的なドメイン型の検査には、次の優先順位を適用する。

| 必要情報の状態 | 確定違反 | 全体の規則結果 | 保持する内容 |
|---|---|---|---|
| 必要な範囲を完全に確認できる | なし | `pass`（正常） | 対象と、公開違反がないことを支える根拠 |
| 必要な範囲を完全に確認できる | あり | `violation`（違反） | 確定した違反とその根拠 |
| 必要情報に未解決または不足がある | なし | `unresolved`（検査不能） | 未解決の対象・範囲・理由 |
| 必要情報に未解決または不足がある | あり | `unresolved`（検査不能） | 確定した違反と未解決理由の両方 |

- **FR5.1**: 実行不能・実行失敗の場合も正常とせず、実行状態と検査不能の理由を呼出し元が区別できるようにする。異なる入力の応答など、信頼できない情報から違反を捏造しない。
- **FR5.2**: 所見と未解決理由は、対象と確認できるソース位置または入力上の範囲へ結び付ける。根拠不足を説明だけの付記へ落とし、全体結果を正常にしない。
- **FR5.3**: 共通契約で`not-applicable`を扱う場合は適用外の証明を必要とする。今回の指定型の欠落、解析未対応、情報不足を適用外に置き換えない。適用外判定のための対象探索は追加しない。

受入条件: 表の四条件を共通判定試験で確認する。特に、確定した公開フィールドと未解決箇所を併せ持つ入力では、結果が検査不能となり、違反も未解決理由も失われない。解析器の起動不能と失敗を与える試験でも正常にならない。

根拠: 要件確認Q1: A、Issue #38、共通検査契約。

### FR6: 再実行可能な検証経路を提供する

両言語の抽出から共通判定までを実行できるコマンドを用意し、今回の対象を自動検証へ登録する。

- **FR6.1**: Rustの二形式とTypeScriptの二形式について、正常・違反・検査不能の代表例を固定し、意味と根拠の対応を比較する。混在時の優先順位、部分的な空集合、不正応答、識別不一致、実行失敗も自動試験の対象とする。
- **FR6.2**: 必要ツール、API版、対応形状、対応しない形状、実行コマンド、期待する結果と終了状態を英日文書へ記載する。実行結果には検証した環境・バージョン・コマンド・成否を残し、未実行の環境まで検証済みとしない。

受入条件: 記載された必要ツールを揃えた環境で文書のコマンドを実行すると、期待値との差が自動検出される。期待値不一致や必要ツール不足で検証コマンドが成功扱いにならない。後続の型解決・移行を実装せずに、この検証を実行できる。

根拠: Issue #38、要件確認、code-structure.md。

## Non-functional Requirements

### NFR1: 結果を再現できること

同じ入力・設定・固定したツール版に対し、規則結果、所見、未解決理由、根拠の対応と順序を再現できること。実行日時などの付帯情報を除く判定結果を繰り返し実行して比較し、一致を確認する。

根拠: Issue #38の再実行可能性、共通検査契約。入力識別の具体的な符号化やハッシュ方式は契約設計で定める。

### NFR2: 既存Rust検査を維持すること

本番センサーの入口・出力契約を切り替えず、既存Rust回帰試験を維持する。今回変更する部分に関係する回帰試験と、新経路の試験を実行し、既存の失敗を隠すために期待値を弱めない。承認済み調査で確認した25件のRust基準試験を比較の出発点とし、変更の影響範囲に応じて必要な検証を選ぶ。

根拠: 要件確認、code-structure.md、[調査時の品質評価](../../../../codekb/base/code-quality-assessment.md)。25件は基準の実績であり、最終的な全試験件数や網羅率の保証ではない。

### NFR3: 言語別抽出と共通判断の境界を検証できること

共通判定を言語別解析器の起動なしでも試験できること。実装と型検査で、共通契約・共通判定がRustやTypeScriptの解析器固有型に依存していないことを確認する。状態公開以外の全情報種別の汎用基盤を先行実装しない。

根拠: Issue #38、architecture.md、要件確認。

性能の数値目標、サービス可用性、認証、業務データの永続化、分散運用の要件は、この開発用検査経路には設定しない。別のNFR・運用ステージを追加せず、入力検証・再現性・回帰防止を上記の受入条件で確認する。

## Constraints

- Rustは既存syn試作を利用し、TypeScriptはCompiler APIの`Program`と`TypeChecker`を使う。文字列照合だけで意味を判定する実装に置き換えない。
- 明示された固定プロジェクト入力で完結させる。パッケージ探索やimport・型別名解決を先行条件にしない。
- 新経路の実装・試験・対応する文書は`ddd/`を対象とする。第三者の`.codex/tools/`、`.claude/tools/`等のフレームワーク実装を変更しない。
- 実行用の`ddd/knowledge`、`ddd/sensors`、`ddd/stages`、`ddd/contributions`は英語とし、それ以外の該当文書は英語版と日本語版を揃える。`aidlc/`の記録は日本語とする。
- 未検証のソース形状を対応済みとしない。後続Issueの成果を暗黙の完了条件にしない。

## Assumptions

- 検査対象と対応表現は呼出し元が明示する。これは合意済みの入力制約であり、型や表現を自動推定するという仮定ではない。
- 検証環境にRustとTypeScript側の必要ツールを用意できることを実行の前提とする。未導入の場合の扱いはFR5.1とFR6.2で検証し、導入済みと決めつけない。
- 「正常」は指定した一規則と対応形状で必要情報を確認できたことを表す。コンパイル全体の成功、すべてのDDD規約への適合、可変参照や副作用の安全性を証明した意味ではない。

要件を成立させるために追加の業務判断を仮置きしている箇所はない。

## Out of Scope

- パッケージ探索、import・型別名の解決、一般の名前解決、全規則の共通化。
- メソッド・ファクトリ固有のエラー集合の照合、汎用的な可変参照・副作用・実行時の状態維持の証明。
- 利用者成果物・設定・`.ddd.toml`の移行、本番センサーの切替、ネイティブバイナリの配布。
- Next.jsやその他のWebフレームワークとの統合、別OSへの対応保証、外部Resultライブラリの選定。

## Open Questions

要件の意味や範囲を左右する未回答事項はない。次の項目は、確認済みの範囲内で後続設計により具体化する。

| 設計で決める項目 | 維持する制約 | 確定する段階 |
|---|---|---|
| 共通情報の具体的な型、版、識別方式、応答検証 | 一規則に必要な最小形式、FR1・FR4・FR5の意味を保持 | 契約設計 |
| コード配置、言語別処理と共通判定の責務 | 本番センサーとの分離、NFR3 | ドメイン設計・作業単位分割 |
| Rust条件付き構文とTypeScript各表現の厳密な対応形状 | 各表現の正常・違反を必ず実装し、判断できない形状は検査不能 | 契約設計・機能設計 |
| 検証コマンド、依存版、固定入力、終了コード | FR6の自動検出・再実行性、既存Rustの回帰維持 | 機能設計・実装・検証 |

これらを決めるために新たな業務判断や解析対象の追加が必要になった場合は、Issue #38の完了条件へ追加せず、親課題へ分離して扱う。
