## ADR-001: 状態公開の共通契約と判定を同じ構成要素が所有する

### Context

対応ストーリー: US1.3（確定違反と検査不能の区別）とUS1.4（共通判定の独立試験）。特にAC1.3.2〜AC1.3.7とAC1.4.5が、情報検証と判定を同じ所有者で扱う境界を裏付ける。

FR4・FR5・NFR3は、情報の確実性と完全性を検証してから、言語に依存せず一規則を判定することを求める。今回扱うのは状態公開だけであり、全情報種別の汎用基盤は対象外である。情報契約を独立させるB案と、判定とまとめるA案を比較し、ユーザーはAを選んだ。

### Decision

StateExposureInspectionが、共通要求・証跡・判定結果の意味と、情報の検証・規則の判定を所有する。検証と判定は別の関数・試験として扱い、未検証の値を正常な根拠として使わない。ほかにRustStateEvidence、TypeScriptStateEvidence、StateExposureVerificationを設け、全体を四つの構成要素とする。

### Consequences

一規則で必要な情報と、その判定を同じ所有者が変更できる。共通検査は解析器を起動せずに試験できる。一方、将来ほかの規則が証跡を独立に使うようになれば、所有境界を分割する検討が必要になる。内部の検証と判定を分けておくことで、その変更余地を残す。

不正な情報を判定へ渡す境界は共通検査側に集約する。共通形式の版や識別の不一致を無視する変換を許さず、情報不足を正常へ変換しない。新たな外部通信や規制対象データの取扱いは追加しない。

### Alternatives Rejected

- **証跡と判定を別の構成要素にする（Q1: B）**: 情報契約の所有者を独立させられるが、一規則でも変更と試験の調整先が増える。今回は独立した変更理由がないため採用しない。
- **言語別処理の中で最終判定まで行う**: 実装は各解析器に近づくが、違反と検査不能の優先順位が二重化する。FR4・FR5の同じ意味の共通判定を満たす境界として採用しない。

## ADR-002: 検証実行が抽出と共通判定を呼び出す

### Context

対応ストーリー: US1.1（Rustの検査）、US1.2（TypeScriptの検査）、US1.4（再実行と回帰検出）。言語ごとの抽出試験、共通判定の独立試験、実際の抽出から判定までの結合検証（AC1.4.1・AC1.4.5）を分けて成立させる。

FR1・FR6は、明示した固定入力に対する抽出から判定までを再実行できる経路を求める。Rust試作には既存の別プロセス境界があり、TypeScriptはCompiler APIを使う。どちらの実行環境も共通判定の前提にすると、NFR3の独立した検証が難しくなる。

### Decision

StateExposureVerificationが入力を確定し、指定言語の抽出処理を呼ぶ。その応答と要求をStateExposureInspectionへ渡し、結果を期待値と比較する。呼出しは応答を待って次へ進む`sync`とし、逆方向の呼出しと循環を設けない。

言語別抽出は共通契約の宣言を参照するが、最終判定を実行しない。共通検査も解析器を呼ばない。ファイル読取り・解析器の選択・実行の準備は検証実行の責務とする。

### Consequences

抽出の固定ケース、共通判定だけの試験、コマンド全体の試験を分けられる。共通検査を実行環境から独立させる代わりに、検証実行が要求と応答の受け渡しを正しく組み立てる必要がある。要求への対応を検証する処理は共通検査に残し、呼出し側の取り違えを検出する。

言語別処理からの未解決理由と実行失敗を結果へ渡し、起動失敗や応答欠落を握りつぶさない。対象ソースは実行せず、既存のコンパイル対照を使う場合も管理された固定ケースに限定する。新しいネットワークサービスは導入しない。

### Alternatives Rejected

- **共通検査が解析器を直接選んで起動する**: 入口は短くなるが、純粋な判定の試験が実行環境へ依存する。言語別の失敗処理も共通検査へ集まるため採用しない。
- **抽出後にイベントで判定へ引き渡す**: 非同期に分離できるが、一つの固定要求に対する検証へ配信・対応付け・完了管理の責務が増える。今回の要件には不要である。

## ADR-003: 共通情報は値とし、検証ケースと実行記録に識別を持たせる

### Context

対応ストーリー: US1.3（要求と根拠の対応）とUS1.4（再現性と実行記録）。AC1.3.1・AC1.3.4は異なる入力の根拠の混在を拒否し、AC1.4.2・AC1.4.6は判定内容と実行ごとの付帯情報を区別する。

FR1・FR4・FR5では、要求・証跡・判定結果が同じ入力と設定に対応している必要がある。FR6・NFR1では、同じケースを繰り返した実行も区別しつつ、判定内容の再現性を確認する。この二種類の識別を同一視すると、runIdの違いで内容一致を誤判定する恐れがある。

### Decision

InspectionRequest、StateEvidence、InspectionResultはStateExposureInspectionが意味を所有する値とする。生成する構成要素が異なっても意味を定義し直さない。解析器の構文・シンボル等は各言語の処理内に閉じる。

StateExposureVerificationがVerificationCaseとVerificationRunを所有する。caseIdはケースの目的を追跡し、runIdは実行を区別する。要求の入力識別はこれらの代わりにせず、再現性の比較は実行ごとの付帯情報と分ける。

### Consequences

情報の所有者と生成者を区別し、同じ証跡を二つの領域で再定義することを避けられる。共通要求や結果に可変の集約・永続化の責務を追加せずに済む。一方、公開形式を決める契約設計では、内容の識別と実行記録の識別を明示しなければならない。

境界間で内部の可変状態を共有せず、違う入力の証跡を混ぜない。対象ソースの全文を実行報告へ複製することは、今回の記録要件ではない。報告には結果と必要な根拠・位置・実行条件を対応付ける。

### Alternatives Rejected

- **要求や証跡をそれぞれ可変のエンティティにする**: 変更履歴を独立に管理できるが、そのライフサイクルや保存を今回の要件は求めていない。
- **実行ごとのIDだけで要求を対応付ける**: 呼出しの追跡には使えるが、ソース・設定の違いや応答の取り違えを検出する根拠として足りない。
- **言語別抽出がそれぞれ共通証跡の意味を所有する**: 言語ごとに変更しやすくなる反面、同じ状態に別の解釈が生じるため採用しない。

## ADR-004: 本番Rustセンサーとの切替を伴わずに新経路を検証する

### Context

対応ストーリー: US1.1・US1.2（両言語の対応形状の検査）とUS1.4（既存Rust回帰と検証範囲の記録）。AC1.4.3・AC1.4.4・AC1.4.6に従い、期待と異なる失敗を検証成功にせず、本番入口・出力契約と実際に検証した範囲を維持する。

現行のInspectionContextにはCargoとRust固有の型が含まれ、syn試作にも指定型・完全性を保証する共通契約はない。FR2・FR3・NFR2はRustの改善とTypeScriptの代表例を扱いつつ、既存Rustの回帰を維持することを求める。本番切替と成果物移行はIssue #38の範囲外である。

### Decision

新経路は既存syn試作をRustStateEvidence内で利用し、既存の本番センサー入口と出力契約を維持する。StateExposureVerificationへ両言語の検証と既存Rust回帰を接続する。試作の終了コードや所見件数を、そのまま規則の合格条件には使わない。

### Consequences

型解決・移行を待たずに今回の成果を統合でき、本番センサーへの影響を限定できる。一方、一時的に二つの経路が存在するため、実行コマンドと対応範囲を英日文書に明記する。今回の検証成功を、本番切替や他OS配布の成功とは扱わない。

新経路で検査できない入力を本番センサーへ自動的に回し、その結果で正常にする代替経路は設けない。第三者フレームワークの実装を変更する前提も置かない。

### Alternatives Rejected

- **既存のInspectionContextを直接拡張する**: 既存呼出しを再利用しやすいが、Rust固有型と探索処理を最小経路へ持ち込むため採用しない。
- **本番センサーを同時に切り替える**: 二経路の併存は減るが、全規則や利用者環境への影響が今回の受入条件を超える。

## Follow-up Design

各判断の具体化は、[components.mdの設計引継ぎ](components.md#design-handoff)に従う。ファイル配置、公開API、厳密な対応形状、IDや版の具体的な形式、エラー応答の詳細を後続設計で定める。ここで選んだ責務の境界と、承認済みの判定の意味を維持する。
