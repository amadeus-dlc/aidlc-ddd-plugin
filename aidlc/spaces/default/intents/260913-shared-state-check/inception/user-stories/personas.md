# 状態公開検査の利用者

## Sources

- [requirements.md](../requirements-analysis/requirements.md): 指定型の検査と再現可能な検証を行う利用者。
- [business-overview.md](../../../../codekb/base/business-overview.md): 規約に沿って実装する開発者と、根拠を確認するレビュー担当者。
- [user-stories-questions.md](user-stories-questions.md): 二つの役割と四つのストーリーの作成方針。

このペルソナは役割を表す。同じ人が両方を担当してもよく、架空の氏名・年齢・組織規模・利用頻度は設定しない。

## P1

**名前:** 検査を利用・保守する開発者

**役割:** プラグインの検査経路を実装・検証し、指定したRustまたはTypeScriptの型について状態公開の結果を確認する。

**目的:** 言語が変わっても同じ規則の意味を維持する。検査対象と設定を明示し、変更後に同じ条件で試験を再実行して回帰を検出する。

**困りごと:** 公開フィールドの取りこぼし、必要情報の不足が正常に見える出力、入力と応答の取り違え、検証条件が分からない報告。

**利用場面:** 開発用コマンドや試験から固定プロジェクト入力を渡し、結果と根拠を確認する。ソース・設定・ツール版を扱う技術的な知識を持つ役割として記述する。

**優先位置:** 主な利用者。US1.1、US1.2、US1.4を担当する。

## P2

**名前:** 検査結果を判断するレビュー担当者

**役割:** 状態公開の違反が確定している箇所と、検査できていない箇所を読み分け、コードや検証結果の妥当性を確認する。

**目的:** 指定した対象の根拠から判断する。全体が検査不能でも、確定した違反を見落とさず、追加確認が必要な範囲を特定する。

**困りごと:** 空の所見一覧だけで合格と見える出力、説明だけに埋もれた未解決事項、別の入力の根拠、再現条件のない結果。

**利用場面:** P1が実行した検査結果と、その対象・位置・条件をレビューする。必要に応じてP1へ入力や検証条件の確認を依頼する。新しい管理画面や認証ロールを設ける指定ではない。

**優先位置:** 判断を行う利用者。US1.3を担当する。

## Persona Relationships

P1が検査を実行して結果と再現条件を残し、P2が確定違反と未解決事項を判断する。両者は同じ対象・設定・根拠を参照し、判定の意味を役割ごとに変えない。P2の確認で情報不足が見つかった場合は、P1が対応範囲内の入力を整えて再実行する。

## Scope Boundary

対象は今回の開発用検査経路である。業務アプリケーションの顧客、運用担当、クラウド管理者などのペルソナは追加しない。ペルソナの優先位置は担当する利用場面を示すもので、Must Haveのストーリーを省く理由には使わない。
