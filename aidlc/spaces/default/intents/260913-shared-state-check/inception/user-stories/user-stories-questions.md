# 状態公開の共通検査 — User Storiesの作成方針

## Sources

- [requirements.md](../requirements-analysis/requirements.md): 承認済みの機能要件21 ID、品質要件3件。再構成時も既存成果物を再利用する。
- [business-overview.md](../../../../codekb/base/business-overview.md): 検査を使う開発者と、根拠を確認するレビュー担当者。
- [component-inventory.md](../../../../codekb/base/component-inventory.md): 既存Rust検査、syn試作、検証経路の現状。
- ユーザーの指定: AI-DLC 2.8.2へこちらのスコープを適合させ、要件→ストーリー→Unitの経路で進行中のintentを再開する。外部への報告は行わない。

## Assessment and Confirmed Context

この工程を実行する。検査結果を使う開発者とレビュー担当者に対して、同じ対象・根拠・判定の意味を提供することが、今回の利用者向けの成果である。言語差、情報不足、確定違反との併存を受入条件として整理する価値がある。

選択したplugin-devでは、対応先2.8.2で扱える要件→ストーリー→Unitの成果物を供給するため、User Storiesを実行する。一般的な開発ツールの内部整理として省略する扱いにはしない。市場調査や新しい業務要件を追加する目的ではない。

以下は承認済み要件とユーザーの指定から確定しているため、再質問しない。

- 対象は状態公開の一規則と、明示したソース・型・設定である。
- Rustの名前付き・タプル構造体、TypeScriptのclass・構造体＋同名コンパニオンを、固定した対応形状で検査する。
- 検査不能を正常へ変換せず、未解決理由と独立に確定した違反を両方保持する。
- 共通契約へ言語固有型を漏らさず、再現可能な検証と既存Rustの回帰確認を行う。
- パッケージ探索、一般の型解決、メソッドエラー集合、利用者成果物・設定の移行、本番切替、ネイティブ配布、Web統合は今回に含めない。
- 四つの構成要素と二つの作業単位の責務分担を引き継ぐ。ストーリーは利用者の成果で分け、必要なら複数の構成要素・単位にまたがる。

## Story Plan

ペルソナは、検査を利用・保守するプラグイン開発者と、検査結果を判断するレビュー担当者の二つとする。架空の氏名・年齢・組織規模を設定せず、役割・目的・困りごと・利用場面を記述する。

| Story ID | 利用者の成果 | 主な要件 |
|---|---|---|
| US1.1 | 開発者が、指定したRust型の状態公開を根拠付きで確認する | FR1、FR2、FR4、FR5 |
| US1.2 | 開発者が、指定したTypeScript型の状態公開を同じ意味で確認する | FR1、FR3、FR4、FR5 |
| US1.3 | レビュー担当者が、確定した違反と検査できない範囲を区別して判断する | FR1、FR4、FR5 |
| US1.4 | 開発者が、同じ条件で検証を再実行し、変更による回帰を検出する | FR6、NFR1、NFR2、NFR3 |

すべて今回の完了条件に必要なMust Haveとする。優先度を付けるためだけの追加機能は作らず、出荷順や日程はこの工程で決めない。

各ストーリーに利用者・目的・便益、Given/When/Thenの受入条件、関係する要件、小さく検証できる範囲、他ストーリーとの依存を記す。IDはUS1.1〜US1.4、受入条件はAC1.1.1の形式で独立に定義する。元のFR・NFRを再採番せず、24 IDすべてを対応付ける。

共通契約の定義と単独判定はU1、言語別抽出と検証実行はU2という責務を前提に、ストーリーの受入条件を割り当てる。利用者の成果の分割と、実装上の依存が同一とは扱わない。再現性・回帰維持の確認には実際の言語別検査との結合が必要であることを明示する。

## Consolidated Summary Confirmation

- 承認済みの要件と分割方針を使い、追加の業務判断なしでUser Storiesを作成する。
- ペルソナはプラグイン開発者とレビュー担当者の二つとする。
- ストーリーはRustの指定型検査、TypeScriptの指定型検査、違反と検査不能の判別、再現・回帰確認の四つとする。
- 全ストーリーをMust Haveとし、利用者・目的・便益、具体的な受入条件、要件との対応、依存と検証可能な境界を記載する。
- 既存の機能要件21 IDと品質要件3件を保持し、独立したストーリーIDと受入条件IDへ対応付ける。IDの付け替えだけでストーリーを作ったことにはしない。
- 四つの構成要素・二単位の責務、検査不能を優先する判定、対象外の範囲を維持する。
- stories.md、personas.md、user-stories-assessment.md、traceability.jsonを作成する。設計・実装・品質の担当者による確認を反映し、その後に独立レビューを行う。
