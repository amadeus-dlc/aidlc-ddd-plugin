### D1: 共通判定の四条件をUS1.3の単独試験として明示する

根拠は上流`requirements.md`のFR5の受入条件「表の四条件を共通判定試験で確認する」と、質問票の「共通契約の定義と単独判定はU1」である。

草案のUS1.3には、部分的な空結果、違反と未解決の混在、情報が完全で違反なしの条件がある。一方、情報が完全で確定違反がある場合の`violation`は、AC1.1.2とAC1.2.3の言語別経路に記載されているだけで、US1.3の受入条件には明記されていない。`traceability.json`でFR5の対応先をUS1.3としているため、現在の記述ではU1の単独完了時に四条件すべてを試験する義務を読み取りにくい。言語別の試験を通すまでU1の判定漏れが分からない構成を避けたい。

US1.3へ次の受入条件を追加する案を推奨する。既存の条件は削らない。

> **AC1.3.7: 共通判定の四条件を単独で確認する**
>
> **Given** 同じ要求に結び付く検証済みの共通情報について、必要範囲が完全か未解決を含むかと、確定違反の有無を組み合わせた四つの固定入力がある。
>
> **When** 言語別解析器を起動せずに共通判定を実行する。
>
> **Then** 完全かつ違反なしは`pass`、完全かつ違反ありは`violation`、未解決を含む二条件は`unresolved`となる。各結果に対応する根拠を保持し、違反と未解決が混在する場合は両方を残す。

これは新要件ではなく、承認済みFR5とNFR3を、U1で実施する試験へ具体化する修正である。具体的な共通型、JSONキー、検証関数のAPIは後続設計に残せる。

### 規模と依存の評価

| Story | 実装可能な境界と引継ぎ事項 |
|---|---|
| US1.1 | 名前付き・タプルの二形式、非公開・公開・未解決の固定入力に閉じられる。syn試作の候補と確定した根拠を区別する処理はU2が担い、共通契約の検証と結果の優先順位はU1を使う。TypeScript抽出への依存は不要。 |
| US1.2 | 二つの表現を扱うため抽出の作業量は大きいが、正常・違反の代表形状と対応外の境界を固定すれば一ストーリーの利用目的として成立する。非公開ブランドの認識に必要な形状と、一般の計算メンバー名を区別し、ブランドを扱うために一般の型解決へ広げない。Rust抽出への依存は不要。 |
| US1.3 | 共通情報の固定入力を使い、U1で契約検証と判定を単独試験できる。D1の補強により、言語別経路の完成を待たずにFR5の全条件を確認できる。 |
| US1.4 | 検証コマンドが期待値の差を検出し、実行条件を残すことに独自の利用価値がある。固定ケース、比較、失敗の伝達、記録の処理を試験できる。最終受入はU1とU2を結合して行うため、US1.1〜US1.3への依存を草案どおり維持する。 |

技術的な依存方向は、U2がU1の共通契約・共通判定を利用する方向である。U1の単独試験を、U2の解析器起動や言語固有型へ依存させない。AC1.4.5は、U1の単独試験と、U2を接続した後の型・依存境界の確認をまとめて検証する条件として扱える。ストーリー数に合わせてUnitや構成要素を増やす必要はない。
