# DDD plugin usage guide

English | [日本語](usage.ja.md)

How to actually use the plugin after installation, for both fresh projects and mid-project (late) adoption. For the installation steps themselves see the [README Quickstart](../README.md#quickstart); for an illustrated view of the mechanism see [architecture.md](architecture.md).

## Prerequisites

1. **The plugin is installed into the target project** — if not, start from the README Quickstart (the one-command installer).
2. **Nothing else** — the code sensors analyze Rust with a vendored tree-sitter-rust WASM grammar, so the target project needs no cargo, Node.js or network.
3. **Confirm** — run `/aidlc --doctor` in a session of the target project and check that the `ddd` stage and sensors are registered (no drops).

## Fresh use (an intent from the start)

**The key is scope selection.** The stage declares `scopes: [enterprise, feature, mvp, classic, workshop, refactor]`, so it runs for intents with those scopes and is SKIPped for any other.

1. Start the workflow with `/aidlc "description of what you want to build"`.
2. Walk the Inception phase. Once `requirements-analysis` and `user-stories` are available, the `ddd-domain-modeling` stage runs:
   - the architect agent discovers domain events, groups them into aggregate candidates, and writes the canonical `domain-model.yaml` (plus the derived `domain-model.md`) under `inception/ddd-domain-modeling/`
   - the write fires `ddd-model-completeness`, which checks conditions (i)–(v): every aggregate has invariants, every command declares its state effect and its domain errors, every referenced ID resolves, and the md agrees with the yaml
   - findings come back as gate feedback; fix the yaml or the md as the Sensors section says
3. Continue to `domain-design`, which (via the plugin contribution) must map every aggregate on the two axes and cite the model IDs, gated by `ddd-model-presence`, `ddd-reference-ids` and `ddd-mapping-declarations`.
4. `functional-design` declares the use cases (six mandatory items, a multi-aggregate strategy) and is checked by `ddd-reference-ids`, `ddd-mapping-declarations` and the advisory `ddd-design-advisories`.
5. `infrastructure-design` declares the layer structure and is checked by `ddd-layer-structure` (rules (k)–(n)) and `ddd-design-advisories`.
6. `code-generation` writes the Rust code and `source-manifest.json`; the write of `code-summary.md` fires `ddd-rust-domain`, `ddd-rust-use-case` and `ddd-rust-interface-adapter` (rules (a)–(n) and the dependency table).

## Late adoption (installing into a project already underway)

Compose is additive, so **installing mid-flight into a project already running AI-DLC affects nothing else**. The relationship between install timing and intents:

| Intent state | Behavior |
|---|---|
| Intents created after the install (in-scope) | The stage joins the execution plan automatically. Same as "fresh use" |
| **Intents already in progress before the install** | The plan has no stage entry, but a single-stage run models them after the fact (below) |
| Out-of-scope intents | SKIP by design; change the scope if you want the stage |

To model an intent that predates the install, make it the active intent and run:

```
/aidlc --stage ddd-domain-modeling --single
```

(The `/ddd-domain-modeling` skill generated by compose is the same thing, packaged.) This single run:

- reads that intent's existing requirements and stories (both optional — a standalone run prompts for the domain vocabulary)
- writes the canonical model under that intent's record
- **never advances the workflow's Current Stage** — it models and stops

When the stage is SKIP, the downstream `ddd-model-presence` sensor passes with a note, so existing intents stay green.

## Reading the outputs

Everything is written under the target intent's record.

- **`inception/ddd-domain-modeling/domain-model.yaml`** — the canonical model: bounded contexts, aggregates, elements, invariants, commands, domain errors, events, transitions, factory rules and `lineage`. Machine-validated by `ddd-model-completeness`.
- **`inception/ddd-domain-modeling/domain-model.md`** — the derived human view. Must mention every element ID and repeat every invariant statement; checked by the (f) rules.
- **`inception/domain-design/ddd-aggregate-mapping.md`** — one row per aggregate: `programming_model` × `persistence_method`, crate/module/repository, and the `reference_ids` it maps.
- **`construction/<unit>/functional-design/ddd-use-case-declarations.md`** — the use cases and their recovery/consistency declarations.
- **`construction/<unit>/infrastructure-design/ddd-layer-structure.md`** — the layer structure: side crates, `crate_dependencies`, ports, repositories, restoration paths.
- **`construction/<unit>/code-generation/code-summary.md`** + **`source-manifest.json`** — the trigger and the exact `.rs` files the code sensors inspect.

## Troubleshooting

- **The stage does not appear in the plan** — check the intent's scope (`Stages to Skip` in `<record>/aidlc-state.md`). Out-of-scope intents SKIP by design.
- **`ddd-model-presence` fails** — `domain-modeling` ran (EXECUTE) but `inception/ddd-domain-modeling/domain-model.yaml` is missing or does not load; run the stage, or fix the model.
- **`ddd-reference-ids` reports `undefined` / `deprecated`** — a declared ID does not resolve against the model. Fix the declaration or the model's `lineage`; a retired ID must not be reused.
- **A Rust sensor reports nothing** — confirm the file is listed in `source-manifest.json` and that its crate resolves to a layer the sensor targets (query-side files are checked by the interface-adapter sensor).
- **A code finding names the wrong rule** — the sensors judge by syntax alone (no type inference). Rule (c-model) and interior mutability are intentionally not machine-checked; they are left to the knowledge documents.
- **`/aidlc --doctor` shows drops** — re-run the installer; it refreshes the plugin's own files before composing and the compose is idempotent.
