# plugin-dev

## Purpose

合意済みの Issue・設計に基づく既存プラグインの機能追加、または公開 API・成果物契約の明示的変更を、構造把握・設計・実装・配布検証まで進める。

この定義は再利用する作業スコープであり、個別の実装依頼ではない。開始時には対象の Issue または具体的な作業依頼を別途指定する。特定の言語や特定の Issue を適用条件にしない。自動キーワード推論は使わず、必要なスコープを明示して選択する。

## Framework Compatibility

- **aidlc-workflows対応基準**: `2.8.2`
- **基準確認日**: `2026-09-13`
- **確認範囲**: スコープ設定、要件→ストーリー→Unitの実センサー検証、不一致Unitの拒否。
- **確認コマンド**: `aidlc --version`、`ddd/`から`bun run test:development-scopes`。

対応基準は、このスコープの設計と検証に使った版を表す。最小対応版の指定や、全工程を通した動作保証を表すものではない。

バージョン更新時は、各工程の入力・出力契約、要件とストーリーのID、Unitへの対応検証、承認・単独実行の検査接続を確認する。変更の影響に応じて`bun run check`とこのスコープの実行経路を検証し、結果を記録してから対応基準と確認日を更新する。版番号だけを先に書き換えない。

## Prerequisites

- 対象は既存プラグインで、対象リポジトリと既存のビルド・テスト・配布検証手順が確認できる。
- Issue または同等の作業依頼と合意済み設計があり、目的・対象範囲・完了条件・今回含めない作業が既に定義されている。
- requirements-analysis は合意を試験可能な受入条件へ整理し、未決の実装詳細だけを質問する。
- AI-DLC 2.8.2でUnitを生成するため、承認済み要件からuser-storiesを作り、要件・ストーリー・Unitの対応を検証する。
- 目的の完了は実装・配布物・利用経路の検証までで、本番配備、新規運用基盤、画面設計、新規 CI 基盤の構築を含まない。
- 少数の Unit を順序付けて進められる。新たなチーム調整や複雑な依存計画が必要になればスコープを再評価する。
- 契約や成果物形式の変更を含む場合は、互換性・移行・既存利用経路の回帰条件を契約設計と build-and-test に必ず含める。

## Workflow

初期化3工程の後に、次の工程を実行する。各工程の EXECUTE / SKIP は scope-grid.json の同名エントリーを正とする。

reverse-engineering → requirements-analysis → user-stories → domain-design → units-generation → contract-design → functional-design → code-generation → build-and-test

requirements-analysis は合意済み事項を受入条件へ整理し、未決の実装詳細だけを質問する。Ideation、独立した NFR、Operation、新規 CI 基盤の構築は含めない。既存の開発手順は reverse-engineering と build-and-test で確認・適用する。

user-storiesは承認済み要件を、利用者・目的・受入条件を持つ最小限のストーリーへ対応付ける。要件IDを維持したまま別のストーリーIDを定義し、要件→ストーリー→Unitを追跡する。IDの付け替えだけでストーリーを作ったことにせず、新しい機能や合意済み事項への再質問を追加しない。

## Verification

- 公開 API・成果物形式を変える場合は、バージョン、互換性、検査結果、明示的な移行方法を契約にする。
- 移行前に対象・変更内容・不足情報を確認できるようにし、安定 ID・参照・意味・既存記録の言語を維持する。不足する業務情報を捏造せず、不正入力時は入力を変更せず、再実行で二重変換しない。
- 変更前の既存テストを基準として記録し、変更後に対象の回帰試験と既存チェックを通す。既存の失敗を今回の成功として扱わない。
- ソースの試験に加え、対象 harness 向けビルド、配布物、compose、導入・更新、通常承認、直接検査の経路を変更の影響に応じて確認する。このリポジトリの対象 harness は Claude Code と Codex。
- 既存の安全性、再実行性、解析時間・資源制約を受入条件と build-and-test に残す。独立した NFR・Operation・CI 構築の工程は設けない。
- 追加した試験は既存のチェックへ接続する。検査不能・不完全な入力・必須成果物の欠落を成功と同一視しない。
- 開発スコープと要件→ストーリー→Unitの対応を、`bun run test:development-scopes`（`ddd/`から実行）でAI-DLC 2.8.2の実コマンドに接続して確認する。正常な対応の合格と、不一致の拒否を両方検証する。
- 実行用の knowledge / sensors / stages / contributions は英語、一般文書は英日を揃え、aidlc/ の作業記録は日本語とする。
- 対応対象のフレームワーク版で扱える入力・成果物を供給する責任は、この開発スコープとプラグイン側にある。既存制約に遭遇したら、まずこちらの設定・生成手順・検査接続を見直す。外部への報告はユーザーの明示指示がある場合に限る。

## Change Control

change_control: relaxed は、承認後の入力変更を一度記録して伝え、処理を継続する。各工程の承認ゲートと、適用前提を外れた変更の再分類は維持する。

## Escalation

- 文書化済みの期待契約へ戻すだけなら plugin-bugfix、公開契約を保つ内部整理なら plugin-refactor を使う。
- 要件が未合意、新規の市場・画面・インフラ・運用設計が必要、または複数チームや複雑な依存へ広がった場合は recompose で必要工程を再評価する。
- 少数 Unit の依存順は units-generation に記録する。単純な順序付けで表せなくなった場合は delivery-planning の追加を提案する。
